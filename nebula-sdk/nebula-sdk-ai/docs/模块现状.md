# nebula-sdk-ai 模块现状梳理

> 生成日期：2026-06-26 ｜ 分支：develop-v1.0.2-SNAPSHOT
> 模块路径：`nebula-sdk/nebula-sdk-ai` ｜ 基础包：`com.nebula.common.ai`

## 1. 模块定位

`nebula-sdk-ai` 是 Nebula 的 **AI 运行时底座 SDK**，对上层业务（如博客 Agent）提供四块统一能力：

1. **AI 调用运行时**：以 OpenAI 兼容协议对接任意厂商（OpenAI / DeepSeek / Moonshot / 通义千问兼容模式 / vLLM 等），统一请求—响应模型。
2. **Agent 抽象**：具备稳定身份（功能编码）、可选记忆、可被编排调度的最小执行单元。
3. **记忆体系**：区分短期会话历史与跨会话长期记忆，按 Agent 维度隔离与配置。
4. **编排内核**：基于 DAG 的多 Agent 协作编排，且编排器自身也是一个带记忆的 Agent。

模块仅依赖 `spring-context` / `spring-boot-autoconfigure` / `httpclient5` / `jackson-databind` / `lombok`，**不绑定具体存储与具体厂商 SDK**，存储与长期记忆均以接口形式留给上层实现。

## 4. 核心能力详解

### 4.1 AI 调用运行时

**调用链**：`AiService.chat()` → 过滤器链 `AiFilterChain` → `AiProviderResolver` 解析 Provider → `OpenAiChatProvider` 发起厂商调用。

- **`AiRequest`**（`domain`）：统一请求体。除常规的 `prompt / messages / model / temperature / maxTokens / topP / stop` 外，关键设计是支持**运行时覆盖**字段 `baseUrl / apiKey / timeoutMs`——优先于全局配置，用于「按节点模型档案动态切换端点与密钥」。
- **`DefaultAiService`**（`service`）：统一入口，职责为「串联过滤器链 → Provider 解析 → 厂商调用」，并在调用前后：
  - 发布 `AiBeforeCallEvent` / `AiAfterCallEvent` 事件；
  - 写调用日志（`AiCallLogger`，可选，失败不影响主流程）；
  - 按需落库会话消息（`AiConversationRepository`，可选，带 `conversationId` 时记录 user + assistant 两条）。
  - 会话仓储与日志记录器均为**可选依赖，缺省即降级为空操作**。
- **`OpenAiChatProvider`**（`provider`）：唯一内置 Provider，经 httpclient5 调 `/chat/completions`，把 `choices[0].message.content` 归一化为统一响应的 `content` 字段；同时透出 `finishReason / model / usage`。

### 4.2 Provider 扩展点

- `AiProvider` 接口 + `AbstractAiProvider` 模板（`buildRequest → execute → parseResponse` 三段式 + `doStream`）。
- `AiProviderResolver` / `DefaultAiProviderResolver` 聚合容器内全部 Provider，按 `provider` 标识路由，未指定时回退默认 Provider。
- 新增厂商只需实现一个 `AbstractAiProvider` 子类并注册为 Bean，无需改动调用方。

### 4.3 Agent 抽象

- **`Agent`** 接口（**已重构为身份+记忆模型**）：`agentCode()`（全局唯一功能编码，作为记忆隔离与编排引用键）+ `memory()`（记忆门面，可为 null）。
- **`AbstractAgent`**：持有 `agentCode` 与 `AgentMemory`，提供统一的身份与记忆访问，业务 Agent 继承后实现具体执行逻辑。
- **`AgentRegistry` / `InMemoryAgentRegistry`**：`register / get(code) / all()`，自动收集容器内全部 Agent Bean。

### 4.4 记忆体系

- **`AgentMemory`** 门面：聚合单 Agent 的短期记忆（会话历史）与长期记忆，**自动以该 Agent 的功能编码隔离**。
  - 短期：`saveMessage / loadHistory（按窗口策略裁剪）/ clearConversation`；
  - 长期：`remember / recall / forget`。
- **`AgentMemoryConfig`**：每个 Agent 可独立配置——短期窗口策略 `MemoryWindow`、是否启用长期记忆、启用哪些长期记忆类型。
- **窗口策略 `MemoryWindow`**：`NoopMemoryWindow`（不裁剪，默认）/ `MessageCountMemoryWindow`（按消息条数）/ `TokenBudgetMemoryWindow`（按 token 预算，配合 `TokenEstimator`）。
- **长期记忆 `LongTermMemory`**（`api`）：语义中立接口（`save / saveAll / search / get / delete / clear`），底层可由向量库 / 检索引擎 / 数据库实现——**SDK 不内置实现**，由上层（如博客 Agent 的 `DatabaseLongTermMemory` + `ai_memory` 表）提供。
- **`MemoryType`** 四类：`SEMANTIC`（语义/事实）、`EPISODIC`（情景/轨迹）、`PROCEDURAL`（程序/流程）、`PREFERENCE`（偏好/画像）。

### 4.5 编排内核（DAG）

- **`Orchestrator`** 接口：`run(OrchestrationGraph, OrchestrationContext)` → `OrchestrationContext`。
- **`DagOrchestrator`**：拓扑排序驱动节点执行，支持节点级**依赖（dependencies）**、**条件跳过（condition）**、**输入映射（inputMapper）**，每节点产出写回上下文供后继消费；带环检测。
- **`OrchestrationNode`**：`code / agent / inputMapper / condition / dependencies / executor(ExecutableAgent) / rememberTrace`。
- **`OrchestrationContext`**：贯穿一次编排的共享状态——`input`、`nodeResults`（`LinkedHashMap` 保留执行顺序以追踪轨迹）、`userId / conversationId`。
- **`OrchestrationAgent`**：把一次编排执行**封装成一个带身份与记忆的 Agent**——执行完成后将编排轨迹作为一条 `EPISODIC` 情景记忆写入长期记忆，实现「编排」与「记忆」的统一，编排器自身也能积累历史。

## 5. 自动装配与启用

`META-INF/spring/...AutoConfiguration.imports` 注册三个装配类：

| 装配类 | 生效条件 | 装配内容 |
|---|---|---|
| `AiAutoConfiguration` | **`nebula.ai.enabled=true`** | `aiHttpClient`、`OpenAiChatProvider`、`AiProviderResolver`、`AiService` |
| `AiAgentAutoConfiguration` | 始终 | `AgentRegistry`（自动注册全部 Agent Bean）、默认 `DagOrchestrator` |
| `AiMemoryAutoConfiguration` | 始终 | `AgentMemoryRegistry`（按容器内 `AgentMemoryConfig` 构建 `DefaultAgentMemory`） |

> 关键约束：**只有 `nebula.ai.enabled=true` 时 `AiService` Bean 才出现**，依赖它的各业务 Agent（如博客 Agent）方可工作。编排与记忆装配始终生效，但具体编排图与 `OrchestrationAgent` 由各业务模块按需定义，SDK 不预置。

## 6. 配置项清单（`nebula.ai.*`）

| 配置键 | 默认值 | 说明 |
|---|---|---|
| `nebula.ai.enabled` | `false` | AI 运行时总开关，关闭则不装配 Provider/AiService |
| `nebula.ai.provider` | `openai` | 默认 Provider 标识，须与某 Provider 的 `getProvider()` 对应 |
| `nebula.ai.openai.provider` | `openai` | 对接非 OpenAI 端点时可改为 deepseek/moonshot 等 |
| `nebula.ai.openai.base-url` | `https://api.openai.com/v1` | OpenAI 兼容根地址（含 /v1） |
| `nebula.ai.openai.api-key` | — | API 密钥 |
| `nebula.ai.openai.model` | `gpt-4o-mini` | 默认模型 |
| `nebula.ai.openai.temperature` | `0.7` | 采样温度 |
| `nebula.ai.openai.max-tokens` | `2048` | 最大输出 token |
| `nebula.ai.openai.top-p` | `null` | 为 null 则不下发 |
| `nebula.ai.openai.timeout-ms` | `60000` | 请求超时（连接获取 + 响应读取） |

## 8. 现状小结与待办

### 已具备
- ✅ OpenAI 兼容同步调用运行时，支持运行时覆盖端点/密钥/超时（按模型档案切换）。
- ✅ 调用前后事件、调用日志、会话落库三类横切能力（均可选降级）。
- ✅ 身份+记忆的 Agent 模型、按 Agent 隔离的短期窗口 + 长期记忆配置。
- ✅ DAG 编排（依赖/条件/输入映射/轨迹），编排器即带记忆 Agent。
- ✅ 自动装配齐备，`nebula.ai.enabled` 总开关控制运行时。

### 待补 / 缺口
- ⚠️ **流式未真正实现**：`OpenAiChatProvider.doStream` 退化为「单次完整调用后整体回调」，未做 SSE 增量解析。
- ⚠️ **仅单一 Provider**：只有 OpenAI 兼容实现，未内置 Anthropic / 其他原生协议 Provider。
- ⚠️ **长期记忆无内置实现**：`LongTermMemory` 仅接口，依赖上层提供（博客模块以 `ai_memory` 表 + `DatabaseLongTermMemory` 落地）。
- ⚠️ **运行时调用链缺测试**：核心 `DefaultAiService` / Provider 调用路径无单测。
- ⚠️ **无重试/熔断/限流**：HTTP 调用失败直接抛 `AiException`，无重试或降级策略。
