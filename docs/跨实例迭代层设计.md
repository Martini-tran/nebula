# nebula 跨实例迭代层设计（Iteration Layer）v2

> 本文档是 [智能体设计.md](./智能体设计.md) 的增补，补齐后者缺失的一层能力：**让一次次 Agent 执行串成一条时间线上的链，上一轮的产出成为下一轮的输入**。原设计只解决"单次执行内部"的状态机（回跳/成环/挂起），本文解决"执行与执行之间"的递推（定时推进、carry-over、落库）。
>
> 触发本设计的真实需求：**"生成一个系列（如 30 天 Java 进阶）→ 每天定时生成一篇 → 每篇都基于上一次的产出（大纲/进度/前几篇）去生成，且大纲边写边规划"**。
>
> v2 修订：一轮 Instance 不一定同步跑到终态，它可能因人工审批或子 Agent 等待进入 `SUSPENDED`。因此新增 **Iteration Run（轮次记录）**，把“本轮已启动但正在等待”和“本轮失败”彻底分开，并让实例在 signal 后到达终态时仍能可靠完成 `advance + Webhook`。

---

## 一、为什么原设计落不了地（问题定位）

原设计的世界观只有两个层级：

```
Agent 定义 ──run──▶ 一个 Instance（从 entry 跑到 terminal，跑完即弃）
```

一个 Instance 是**封闭的**：进 Inputs、出 Outputs，然后结束。它内部能成环、能挂起，但**没有任何东西表达"这次的 Outputs 要成为下次的 Inputs"**。而"系列逐天生成"的本质就是一句话：

> **上一次实例的 Outputs = 这一次实例的 Inputs，如此递推 N 次。**

这不是某个业务概念的特殊需求，而是**编排引擎缺了"跨实例递推"这一等能力**。原设计有"成环（同一实例内循环）"，但成环是**同一个实例内部**的循环，跑完就结束，无法"停一天再继续下一圈"。

### 1.1 两个正交的循环维度

| 维度 | 循环发生在 | 时间尺度 | 承载物 | 现状 |
|---|---|---|---|---|
| **实例内循环**（原设计） | 一个 Instance 内部（成环/回跳） | 秒~分钟 | `context_snapshot` + 转移历史 | ✅ 已落地 |
| **实例间递推**（本设计） | Instance 与 Instance 之间 | 天级（定时） | 上一轮 `instance.outputs` + 链表 | ✅ 基础链已落地；挂起轮次异步收口按 v2 补齐 |

"系列"不是"成环成得久一点"，它是**另一个维度**。试图用"挂起等定时器 30 天"去凑，会踩三个坑（见 1.2）。

### 1.2 三条凑法为什么都不行（明确排除）

| 凑法 | 为什么不行 |
|---|---|
| **状态机成环 + 挂起等定时器** | 一个实例挂 30 天违背"跑完即弃"；`context_snapshot` 越滚越大；挂起态本为 Human-in-loop 设计，不是为"每天定时唤醒 N 次"。 |
| **靠长期记忆 `ai_memory` 传前几篇** | 记忆按 `agent_code` 跨版本**共享、无序、无"第几篇"概念**；且原设计明确 Import 定格、Export 尽力而为（可失败不翻盘）——而"第 2 篇必须读到第 1 篇"是**强依赖**，不能尽力而为。 |
| **父子递归 AgentNode** | 递归是"一次执行内**同步**调子 Agent"，父实例不可能挂 30 天等 30 个子实例异步跑完。 |

### 1.3 记忆的两层分工（解开"记忆没法落地"的核心困惑）

需求里的"上次记忆"，**不是** `ai_memory`，而是**这条链上一轮实例的 Outputs**。两者职责必须分清：

| 记忆种类 | 是什么 | 特性 | 存哪 | 归谁管 |
|---|---|---|---|---|
| **系列递进状态** | 这一个系列的递推链：大纲/进度/前几篇 | **有序、强一致、有"第几篇"、崩了不丢** | 上一轮 `ai_agent_instance.outputs`（+ 链表指针） | **本设计的 IterationDriver** |
| **Agent 长期记忆** | 跨系列的、Agent 级的静态认知（如"这个博客的整体调性"） | 无序、跨版本共享、尽力而为 | `ai_memory`（原设计） | 原设计 Import/Export 钩子 |

**结论**：系列递进走"上一轮 outputs → 下一轮 inputs"的强一致通道，与 `ai_memory` 正交、互不替代。

## 二、核心抽象：迭代链（Iteration Chain）

不新增"系列"这个业务专名，而是补上编排缺失的**通用递推**能力——它不只能写博客，还能做任何"每轮基于上轮结果推进"的长任务（连载、周报、多轮精炼、递归调研）。

```
┌──────────────────────────────────────────────────────────────┐
│  迭代链 ai_agent_iteration（长期存在，天级，被定时驱动）           │
│  chain_id / agent_code / cron / next_run_at / seq / until /   │
│  last_instance_id / status(ACTIVE|RUNNING|WAITING|PAUSED|...) │
└──────────────────────────────────────────────────────────────┘
        每到 cron 点，推进一轮 ▼                    ▲ 回写链（advance）
┌──────────────────────────────────────────────────────────────┐
│  单篇实例 ai_agent_instance（短期，分钟级，跑完即弃）——原设计不改   │
│  创建时把上一轮 outputs 按 carryOver 映射为本轮 inputs 注入        │
│      ▼                                                        │
│  你已有的状态机：[生成]→[评分]→回跳重写→[terminal]                 │
│      ▼                                                        │
│  terminal 时引擎把产出落 instance.outputs（原设计已有，不用工具）    │
└──────────────────────────────────────────────────────────────┘
```

- **一条链 = 一个"系列"实例**。链是长期状态载体，实例是链上被反复创建的一个个节点。
- **链靠 `last_instance_id` 指针串起时间线**，无需扫描（也可选复用 `parent_instance_id`，见 4.3）。
- **每一轮实例仍是干净的、跑完即弃的 Instance**——完全复用原设计的实例表、状态机内核、恢复四铁律，**内核一行不改**。

### 2.1 三个需求点如何各自对上

| 需求 | 本设计如何实现 |
|---|---|
| **定时自动（每天一篇）** | 链持有 `cron`/`next_run_at`，由 `IterationDriver` 定时扫描、到点推进一轮（不让实例挂 30 天）。 |
| **看到前面篇章（大纲/进度 + 累积状态 + 前几篇摘要）** | 每次创建实例时，Driver 读上一轮 `instance.outputs`，按 `carryOver` 映射为本轮 `inputs` **显式注入**——强一致、有序、有"第几篇"。 |
| **边写边规划（大纲动态涌现）** | `outline` 是实例产出的一部分：每轮实例不仅写文章，还**更新大纲**（下一篇写啥），回写进 outputs。下一轮读到的就是被上一轮改过的大纲。 |

## 三、落库讲清楚：四类状态、四个责任边界

"落库"在直觉里是一坨，v2 拆成四类不同状态。前两类由 Agent Runtime 管，后两类由 Iteration Layer 管；Agent 内部节点仍不直接操作链表。

| # | 落什么 | 谁落 | 时机 | 现状 |
|---|---|---|---|---|
| ① | **单篇实例本身**（状态、转移历史） | `AgentEngine` 内部 `instanceStore.create()` + `StoreBackedTransitionListener` | 实例创建 + 每次转移 | ✅ [AgentEngine.java:159](../nebula-sdk/nebula-sdk-ai/src/main/java/com/nebula/common/ai/agent/AgentEngine.java#L159)/[:183](../nebula-sdk/nebula-sdk-ai/src/main/java/com/nebula/common/ai/agent/AgentEngine.java#L183) |
| ② | **单篇产出 Outputs**（文章正文、更新后的大纲） | 内核把 context delta 写进 `transition.node_result`，终态刷 `context_snapshot` | 实例到 terminal | ✅ `markTerminal(...)` |
| ③ | **轮次执行 Run**（本轮哪个实例、运行/等待/失败） | `IterationDriver` + `IterationRunStore` | 预约本轮、绑定实例、挂起或终态 | v2 新增 |
| ④ | **链的推进**（写到第几篇、下轮何时跑、上轮是哪个实例） | `IterationCompletionCoordinator` | 本轮最终 SUCCESS 后 | v1 已有基础 advance，v2 统一收口 |

### 3.1 关键澄清：③④ 都不在 Agent 内部落

一直纠结的"是不是要在 Agent 最后加个工具去 insert 数据"——**不需要**。①② 是运行时职责；③④ 是迭代层职责。实例可以同步完成，也可以挂起数小时后完成，但最终都由同一个 `completeRound` 收口。

```java
IterationRun run = iterationCoordinator.reserve(chain); // ③ 预约轮次，Chain→RUNNING
OrchestrationContext ctx = agentEngine.run(agentDef, inputs, userId, convId);

if (isSuspended(ctx)) {
    iterationCoordinator.markWaiting(run.runId(), currentInstanceId(ctx)); // ③ WAITING
    return; // 释放调用线程，稍后由实例终态事件继续
}
if (isSuccess(ctx)) {
    iterationCoordinator.completeRound(run.runId(), currentInstanceId(ctx), ctx); // ③终态 + ④advance
}
```

它不需要 Agent 内部增加落库工具。`IterationCoordinator` 是普通编排层代码，不受“节点只能写 Context”的限制；但它必须遵守 Run CAS、Chain CAS 和事务边界，不能再用一次无状态 mapper 更新概括全部生命周期。

### 3.2 为什么不能"Agent 里加个工具去落库"（再钉一次）

- **工具看不到链**：工具节点写库只知道"当前这一篇"，不知道 `chainId`/`seq`/`cron`/`nextRunAt`——这些是链的元数据，只有链的管理者 Driver 有。让工具写链 = 让"一篇文章"去管"整个系列的排期"，职责彻底错位。
- **中途写库会脏**：工具在状态机中途执行，万一后面节点失败回跳，这条链数据就脏了。
- **正确分工**：Agent 只把产出留在 `ctx` 里（它已经会了）；链的落库交给外层看得见全局的 Driver。**carry-over 是"读上一轮 outputs 列"，不是"往新表插数据"。**

### 3.3 关联设计：把产物落进业务库（如 blog）走回调，不走本层

本章的"落库"指的是**链账本**（`ai_agent_iteration` 的推进）与**实例产物**（`ai_agent_instance`）。但"每轮生成的文章要落进 **blog 业务库**"是**另一回事**——那是产物的**业务消费**，不属于迭代层。

它由独立的**编排回调（Webhook）**机制承接：Driver 在 `advance` 成功后，把产物 POST 到配置的回调 URL，blog 起个接口接住、幂等落库。引擎/Driver **不认识 blog**，只认 URL。详见：

> **[编排回调Webhook设计.md](./编排回调Webhook设计.md)**：`ai_webhook_delivery` 投递记录（日志+断点续发）+ 三触发点分离（迭代链走 advance 后触发）+ 可靠性只归 delivery 表与重发。

## 四、数据模型（DDL）

沿用原设计 `ai_` 前缀、`ai-flow` store 模块风格（`@TableName`、`FieldFill`、JSON 列以字符串存 + `FlowJsonCodec`）。**只新增一张极轻的链表**，不动 `ai_agent` / `ai_agent_instance`。

```sql
CREATE TABLE ai_agent_iteration (
  id                BIGINT       PRIMARY KEY AUTO_INCREMENT,
  chain_id          VARCHAR(64)  NOT NULL COMMENT '迭代链唯一标识，业务键（= 一个"系列"实例）',
  name              VARCHAR(128)          COMMENT '链名称，如"30天Java进阶"',
  agent_code        VARCHAR(64)  NOT NULL COMMENT '每一轮用哪个 Agent 跑（跨版本稳定，运行时取该 agent_code 最新启用版本或锁定版本）',
  cron              VARCHAR(64)  NOT NULL COMMENT '推进节律，如 "0 0 9 * * ?"（每天9点）',
  next_run_at       DATETIME     NOT NULL COMMENT '下一轮应触发时间（Driver 扫这个字段决定谁到点）',
  seq               INT          NOT NULL DEFAULT 0 COMMENT '已完成轮次（= 已写到第几篇）',
  max_iterations    INT                   COMMENT '轮次上限（可空，防无限连载；到顶置 COMPLETED）',
  until_expr        VARCHAR(512)          COMMENT '出链条件 SpEL（复用 ConditionCompiler），如 "outline.done == true"；对上一轮 outputs 求值',
  carry_over        TEXT                  COMMENT '★carry-over 映射(JSON)：上一轮 outputs 的哪些键 → 下一轮 inputs 的哪些键',
  seed_inputs       TEXT                  COMMENT '首轮种子入参(JSON)：第 0 轮没有上一轮，用它启动（如系列主题）',
  last_instance_id  VARCHAR(64)           COMMENT '上一轮实例 id（carry-over 数据源指针；首轮为空）',
  user_id           VARCHAR(64),
  conversation_id   VARCHAR(64),
  status            VARCHAR(16)  NOT NULL DEFAULT 'ACTIVE' COMMENT 'ACTIVE | RUNNING | WAITING | PAUSED | COMPLETED | FAILED',
  consecutive_fails INT          NOT NULL DEFAULT 0 COMMENT '连续失败次数，达阈值自动 PAUSED（防定时打空转）',
  error_msg         TEXT                  COMMENT '最近一次推进失败原因',
  lock_version      INT          NOT NULL DEFAULT 0 COMMENT '乐观锁（可选，配合 Redis 锁双保险）',
  create_time       DATETIME,
  update_time       DATETIME,
  UNIQUE KEY uk_chain_id (chain_id),
  KEY idx_due (status, next_run_at)  -- Driver 扫描 WHERE status='ACTIVE' AND next_run_at<=now() 走此索引
) COMMENT='AI 智能体跨实例迭代链（系列递推）';
```

### 4.1 `carry_over` 结构

```jsonc
// ai_agent_iteration.carry_over —— 上一轮 outputs 键 → 下一轮 inputs 键
{
  "outline":     "outline",       // 上轮产出的大纲 → 下轮同名入参
  "accumulated": "accumulated",   // 累积写作状态（用过的例子/讲过的知识点/风格基调）
  "articleIndex":"history",        // 已写文章索引 → 下轮入参名 history
  "seq":         "prevSeq"         // 也可带上"这是第几篇"给 Agent 感知
}
```

> **只映射"引用/摘要"，不搬全文字节**：与原设计 Artifacts 存 key 一致——`articleIndex` 里每篇只存 `{title, summary, ossKey}`，前几篇全文按需由 Agent 从 oss key 拉取，避免 carry-over 载荷随篇数膨胀。

### 4.2 首轮 vs 后续轮的 inputs 来源

- **首轮（seq=0，`last_instance_id` 为空）**：inputs = `seed_inputs`（系列主题等种子）。
- **后续轮（seq>0）**：inputs = 读 `last_instance_id` 那个实例的 `outputs`，按 `carry_over` 映射。**若 seed 里有 carry 没覆盖的键（如恒定的系列主题），做浅合并，carry-over 值优先。**

### 4.3 链靠指针串联，不扫描

`last_instance_id` 一个指针即可回溯"上一轮产出"。是否再复用 `ai_agent_instance.parent_instance_id` 把整条链串成父子链（便于回放整条时间线）是**可选增强**：链短、只需上一轮时不必；需要"回放整个系列 30 篇"时启用，让第 N 篇的 `parent_instance_id` 指向第 N-1 篇。

### 4.4 新增 `ai_agent_iteration_run`：一轮的可靠执行信封

原 v1 直接在 `IterationDriver` 的调用栈中等待 `agentEngine.run()` 返回，然后立即 `advance`。这只覆盖“当场跑到终态”的实例；若实例 `SUSPENDED`，调用栈结束后没有持久化对象负责在数小时后接住 signal 的终态结果。

**决策**：Chain 表达长期递推位置，Iteration Run 表达某一轮已经启动的执行。二者不能混用。

```sql
CREATE TABLE ai_agent_iteration_run (
  id              BIGINT       PRIMARY KEY AUTO_INCREMENT,
  run_id          VARCHAR(64)  NOT NULL COMMENT '轮次执行标识',
  chain_id        VARCHAR(64)  NOT NULL,
  target_seq      INT          NOT NULL COMMENT '准备完成的轮次，等于创建时 chain.seq + 1',
  attempt         INT          NOT NULL DEFAULT 1 COMMENT '同一轮第几次尝试',
  instance_id     VARCHAR(64)           COMMENT '承载本轮的 Agent Instance',
  status          VARCHAR(16)  NOT NULL COMMENT 'PENDING|RUNNING|WAITING|SUCCESS|FAILED|CANCELLED',
  outputs         TEXT                  COMMENT '终态输出引用/摘要；权威原文仍在 instance',
  error_msg       TEXT,
  lock_version    INT          NOT NULL DEFAULT 0,
  create_time     DATETIME,
  update_time     DATETIME,
  UNIQUE KEY uk_run_id (run_id),
  UNIQUE KEY uk_chain_seq_attempt (chain_id, target_seq, attempt),
  UNIQUE KEY uk_instance_id (instance_id),
  KEY idx_chain_status (chain_id, status),
  KEY idx_status_update (status, update_time)
) COMMENT='AI 迭代链单轮执行记录';
```

职责：

- 防止 Chain 为 `RUNNING/WAITING` 时定时扫描器重复启动同一轮。
- 记录 signal 前后的挂起轮次，建立 `instance_id → chain_id/target_seq` 的可靠反查。
- 同一 target_seq 失败重试时保留 attempt 历史，不覆盖失败实例。
- 实例终态事件到达时，即使原 Driver 调用栈早已结束，仍可完成链推进。

## 五、IterationDriver 执行时序（多实例安全）

多实例部署 + Redis：**Redis 只做"谁来跑、什么时候跑"，MySQL 做"跑到哪了、跑出了啥"**。掉电 Redis 空了不影响链的接续——链表和实例 outputs 都在 MySQL。

```text
每个节点都有 @Scheduled（每分钟扫一次）
        ▼
① 扫 Chain：status='ACTIVE' AND next_run_at<=now
        ▼
② 抢 Redis 锁：SET NX EX（只减少并发竞争，MySQL CAS 才是正确性边界）
        ▼
③ 一个事务预约本轮：
   INSERT ai_agent_iteration_run(PENDING, target_seq=chain.seq+1)
   CAS Chain ACTIVE → RUNNING
        ├─ CAS 失败：别人已预约，放弃
        └─ CAS 成功 ▼
④ 组装 inputs：seed 或 last_instance.outputs + carry_over
        ▼
⑤ 创建 Agent Instance，并把 instance_id 回写 Iteration Run：PENDING → RUNNING
        ▼
⑥ 执行实例：
   ├─ SUCCESS   → 统一调用 completeRound(...)
   ├─ SUSPENDED → Run=WAITING，Chain=WAITING；释放线程和 Redis 锁
   └─ FAILED    → Run=FAILED；Chain 按失败策略回 ACTIVE/PAUSED
        ▼
⑦ 若实例稍后被 signal 唤醒并到达终态：
   AgentInstanceLifecycleListener
     → 按 instance_id 找 Iteration Run
     → 再调用同一个 completeRound(...)
        ▼
⑧ completeRound 一个事务：
   CAS Run RUNNING/WAITING → SUCCESS
   CAS Chain WHERE seq=target_seq-1 AND status IN(RUNNING,WAITING)
     → last_instance_id=instanceId, seq=target_seq,
       next_run_at=下个 cron, status=ACTIVE/COMPLETED
        ▼ 事务提交后
⑨ Webhook Dispatcher 投递本轮产物
```

`completeRound` 是同步完成与异步唤醒的**唯一收口入口**，禁止在 `signal` Controller、`AgentEngine` 和 `IterationDriver` 中各写一套推进逻辑。

### 5.1 Redis 锁的两个作用点

1. **减少并发预约竞争**：多节点同时扫到一条到点链时，通常只有抢到锁的节点进入 MySQL 预约事务。
2. **崩溃后允许接管**：持锁节点崩溃后 key 到期；后续节点读取 Iteration Run 判活并用 CAS 接管，而不是无条件重建实例。

v2 修订后，Redis 锁过期不能直接再创建新实例：扫描器先检查 Iteration Run。若存在 `PENDING/RUNNING/WAITING` 的当前轮记录，则进入恢复/判活逻辑；只有确认旧 Run 已失败或租约失效并完成 CAS 接管，才创建新 attempt。

### 5.2 幂等与"至少一次"

与原设计一致：Driver 层是 **at-least-once**（锁到期 + 重扫可能让同一轮跑两次）。若一轮内有外部副作用（如发布到公众号），该动作须自带幂等键（如 `chainId + seq`），靠下游去重。链推进本身（`advance`）是幂等的：`advance` 用 `WHERE chain_id=? AND seq=?`（乐观锁）保证同一轮只推进一次。

```sql
-- advance 带 seq 断言，防同一轮被推进两次（配合 Redis 锁双保险）
UPDATE ai_agent_iteration
SET last_instance_id=?, seq=seq+1, next_run_at=?, status=?, consecutive_fails=0, update_time=now()
WHERE chain_id=? AND seq=? AND status IN ('RUNNING','WAITING');
-- 影响 0 行 = 状态/seq 已变化，本次 completeRound 放弃
```

v2 实现时该 SQL 应收口进 `completeRound`，并允许 Chain 从 `RUNNING/WAITING` 完成；`Iteration Run` 的状态 CAS 与 Chain advance 必须处于同一数据库事务。Webhook 仍在事务提交后触发，失败只重投 payload，不回滚链。

### 5.3 挂起不是失败

- Instance `SUSPENDED` → Iteration Run `WAITING`、Chain `WAITING`。
- 不增加 `consecutive_fails`，不顺延下一轮，不重复创建实例。
- 人工 signal 或子任务终态事件唤醒 Instance；若再次挂起，Run/Chain 继续 WAITING。
- Instance 最终 SUCCESS 才 advance；最终 FAILED 才进入链失败策略。
- 管理端可对 WAITING 轮次执行查看、催办、signal、取消；不能把它当失败重试。

## 七、REST / manager 侧

沿用 `/admin/ai-flow` 风格（manager 默认 camelCase，见 memory `manager-json-camelcase`）：

- `POST   /admin/ai-iteration`（创建链：agentCode + cron + carryOver + seedInputs + until）
- `GET    /admin/ai-iteration/{chainId}`（链详情 + 已产出实例时间线：按 `last_instance_id`/`parent_instance_id` 回溯）
- `POST   /admin/ai-iteration/{chainId}/pause` | `/resume`（PAUSED ↔ ACTIVE）
- `POST   /admin/ai-iteration/{chainId}/run-now`（手动立即推进一轮，绕过 cron；仍走 Redis 锁）
- `GET    /admin/ai-iteration/{chainId}/runs`（轮次与 attempt 历史，包含 WAITING）
- `POST   /admin/ai-iteration/{chainId}/runs/{runId}/cancel`（取消当前挂起/运行轮次）
- `DELETE /admin/ai-iteration/{chainId}`（停链；不删已产出实例）

> `run-now` 让"手动逐次触发"和"定时自动"共用同一条推进路径——手动只是把 `next_run_at` 置为当前并触发一次扫描。

## 八、落地路线（接原设计阶段路线之后）

原设计阶段 1~4 已把状态机内核 / Agent 层 / 挂起递归 / REST 落地。本层作为其上的**独立增量**，不依赖阶段 2.5（补偿）：

**迭代层阶段 I · 链表 + Driver（核心）**
- `ai_agent_iteration` 表 + `IterationChainStore` SPI + `DatabaseIterationChainStore`
- `IterationDriver`：`@Scheduled` 扫描 + Redis 抢锁 + carry-over + 调 `AgentEngine.run` + `advance`
- carry-over 映射器（读上轮 `contextSnapshot` → 组装 inputs）
- **Demo：博客系列**——首轮据主题生成大纲+第 1 篇，后续轮读上轮大纲/累积状态/文章索引生成下一篇，大纲边写边调，`until = outline.done`
- 单测：首轮种子启动 / 后续轮 carry-over / until 出链 / max_iterations 封顶 / Redis 锁防重跑 / advance 乐观锁幂等

**迭代层阶段 II · 韧性与运维**
- 连续失败自动 PAUSED + 告警；`run-now` 手动补跑；REST + manager 页面（链管理 + 时间线回放）
- 可选：`parent_instance_id` 串全链，支撑"回放整个系列 N 篇"

**迭代层阶段 II.5 · 挂起轮次异步收口（v2 必做）**
- `ai_agent_iteration_run` + `IterationRunStore`
- Chain `RUNNING/WAITING` 状态
- `IterationCompletionCoordinator.completeRound`
- 实例生命周期 Outbox/Listener
- signal 后终态自动 advance + Webhook
- 故障测试：预约后崩溃、挂起后重启、终态事件重复投递、双节点同时 complete

**迭代层阶段 III · 增强（按需）**
- 动态节律（Agent 产出里带"下一轮几天后跑"，覆盖固定 cron）
- 分支链（一条链某轮产出触发派生子链）
- 与 `ai_memory` 协同：系列级累积状态在链结束时归纳进 Agent 长期记忆

## 九、决策记录

- ✅ **递推是编排缺的一等能力，不是业务专名**：新增通用"迭代链"，博客系列是其首个用例。
- ✅ **系列递进状态走"上轮 outputs → 下轮 inputs"强一致通道，不走 `ai_memory`**（后者是 Agent 级静态认知，尽力而为，无序，不满足强依赖）。
- ✅ **四类状态分责任边界**：①实例②产出由 Runtime 落；③轮次 Run ④Chain advance 由迭代层落；均不依赖 Agent 内工具。
- ✅ **迭代驱动在 Agent 外部**：定时/carry-over/落库/判下一轮全是编排层职责，Agent 只管"跑一篇"，对链无感知。
- ✅ **Redis 管调度（锁 + 到点），MySQL 管状态（链表 + 实例 outputs）**：掉电 Redis 空了不断链。
- ✅ **多实例靠 Redis `SET NX EX` 防重跑 + `advance` 乐观锁双保险**，无需引入 Quartz/xxl-job/ShedLock。
- ✅ **每轮仍是干净的跑完即弃 Instance**：内核 / 实例表 / 恢复四铁律一行不改。
- ✅ **carry-over 只搬引用/摘要不搬全文字节**（对齐原设计 Artifacts 存 key），载荷不随篇数膨胀。
- ✅ **Driver 层 at-least-once**：有外部副作用的轮次自带幂等键（`chainId+seq`）交下游去重。
- ✅ **挂起不是失败**：轮次进入 WAITING，不累计失败、不顺延、不重建实例；终态后再统一收口。
- ✅ **新增 Iteration Run**：Chain 管长期位置，Run 管本轮执行与 attempt；实例终态可按 instanceId 反查所属轮次。
- ✅ **同步/异步共用 completeRound**：不在 Driver、signal Controller、AgentEngine 分别实现 advance。
- ✅ **Run 终态 CAS + Chain advance 同事务，Webhook 提交后触发**。
