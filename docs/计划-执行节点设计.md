# nebula 计划-执行（Plan-and-Execute）设计 v2

> 本文档是 [智能体设计.md](./智能体设计.md) 的增补，回答一个具体问题：
> **"想让 AI 生成计划 → 写入计划 → 按计划执行，应该创建一个什么样的节点？"**
>
> 核心结论先说：**大多数情况下不需要新节点类型**。"生成计划→按计划执行"在本架构里是
> **状态机的一种成环模式**，用现有 `LLM + IF + 成环边` 即可表达；"写入计划"= 把计划数组
> 写进 `ExecutionContext`（自动落 `transition.node_result`），**不建计划表、不加落库工具**。
> 只有当这个模式被高频复用、手写 guard 成为痛点时，才抽象出 `PLAN` 节点作为**语法糖**。
>
> **评审已定的基础形态（见第六章）**：跨天连载（迭代链）+ 每轮内 [规划 → 人工审批(真挂起) →
> ReAct 里程碑执行 → 产物 Webhook 落库]。`AgentReactNodeExecutor` 已编码；v2 进一步区分两种执行方式：
> 单个 Agent 在里程碑内自主调工具，或 Lead Agent 把不同里程碑动态委派给多个专业 Worker Agent。后者见
> [多智能体协作层设计.md](./多智能体协作层设计.md)。

## 〇、先厘清：你的"计划"是哪一类（决定走哪条路）

"生成计划→执行"这句话在本架构里对应**三种正交的时间尺度**，用错层会像 [跨实例迭代层设计.md](./跨实例迭代层设计.md) 1.2 节"用挂起凑系列"一样别扭。

| 类型 | 例子 | 时间尺度 | 承载物 | 对应架构层 | 要不要新节点 |
|---|---|---|---|---|---|
| **A. 单实例内步骤计划** | "查资料→列纲→逐段写→润色"，一口气跑完 | 秒~分钟 | `context.plan`（固定步骤） | 状态机内核（`engine_type=STATE_MACHINE`） | ❌ 不要 |
| **B. 动态待办清单** | AI 运行时列出 N 个子任务，逐个做，做完勾一个 | 分钟 | `context.plan`（运行时长度） | 状态机成环 + IF guard | ❌ 不要（可选 PLAN 语法糖） |
| **C. 跨天/跨实例连载** | 生成 30 天大纲→每天写一篇→边写边改大纲 | 天级 | 上轮 `instance.outputs` + 迭代链 | 迭代链 `ai_agent_iteration` | ❌ 不要（迭代层已覆盖） |

> **关键认知**：A/B 是"一次执行内部"的计划（成环），C 是"执行与执行之间"的计划（迭代链）。
> 三者都**不需要新建节点类型**——A/B 用现有节点组合，C 用现有迭代层。新节点只在 B 想要
> 语义化封装时才可选（第四章），且本设计**建议缓做**。

## 一、为什么"不需要新节点"——把三条铁律对齐一遍

"生成计划→写入计划→按计划执行"三个动作，在本架构里各自已有归宿：

| 动作 | 直觉做法（❌） | 本架构正确做法（✅） | 依据 |
|---|---|---|---|
| **生成计划** | 造个"计划生成节点" | 普通 **LLM 节点**，用 `outputKey` 把计划数组写进 context | 现有 `PromptNodeExecutor` |
| **写入计划** | 加个工具节点 `insert into plan_table` | **写进 `ExecutionContext`**，引擎自动落 `transition.node_result`（context delta） | 智能体设计 二·3；迭代层 3.2 |
| **按计划执行** | 造个"计划执行器"轮询计划表 | **状态机成环** + IF 节点的 `condition_expr`(SpEL) 对 `context.plan` 求值决定是否继续 | 智能体设计 5.3 转移裁决 |

**三条已有铁律直接复用，一条都不用新增：**

1. **"计划=context 里的数据，不是数据库表"**：计划由 LLM 节点写进黑板，`node_result = context delta`
   （智能体设计 二·3）自动把这次写入落库。崩溃恢复靠增量重放 SUCCESS 转移**自动还原计划**，
   无需任何"计划表"。这正是迭代层 3.2 反复钉的"**不要在 Agent 里加工具写库**"。
2. **"按计划执行=guard 成环"**：IF 节点出边的 `condition_expr`（复用 `ConditionCompiler`）对
   context 里的 plan 求值，决定"还有未完成项→回跳执行 / 全部完成→去终态"。回跳/成环正是状态机
   内核相对 DAG 的核心能力（智能体设计 5.1）。
3. **"防死循环有兜底"**：`max_transitions`（智能体设计 5.3，per-Flow 可配默认 100）保证 plan 再长
   也不会无限循环，超限置 FAILED。

## 二、方案 A/B：Plan-and-Execute 成环结构（推荐首选）

**不加任何新节点**，用现有 `LLM / TOOL / IF` + 成环边表达。这是智能体设计阶段 1 demo
（自我审查循环）的同构变体。

### 2.1 图结构

```text
[ENTRY] 规划节点(LLM)
   │   prompt: "把目标拆成有序子任务，输出 JSON 数组"
   │   outputKey: plan   → context.plan = [
   │                          {"id":1,"step":"查资料","tool":"search","done":false},
   │                          {"id":2,"step":"列提纲","done":false}, ...]
   ▼
执行节点(LLM 或 TOOL)
   │   取 plan 里第一个 done=false 的项执行
   │   结果写回该项，标记 done=true，产物写进 context（如 context.results[id]）
   ▼
[IF] 计划是否还有未完成项？
   ├─ guard: #hasPending(plan)  ──────────▶ 回跳「执行节点」（成环，做下一项）
   └─ guard: 空表达式(default)  ──────────▶ [TERMINAL] 汇总节点 → 输出 Outputs
```

### 2.2 每个节点落什么（对齐现有 nodeConfig 结构）

| 节点 | 类型 | 关键配置 | 写进 context 的键 |
|---|---|---|---|
| 规划 | `LLM`（`state_type=ENTRY`） | prompt=拆解目标；`output.type=JSON`；outputKey=`plan` | `plan`（数组） |
| 执行 | `LLM` 或 `TOOL` | prompt/工具=执行单个子任务；读 `plan` 取待办项 | `plan`(更新 done)、`results` |
| 判断 | `IF` | 出边 guard 见下 | — |
| 汇总 | `LLM`（`state_type=TERMINAL`） | 把 results 归纳成最终输出 | `outputs` |

### 2.3 guard 表达式（复用 `ai_flow_edge.condition_expr` + SpEL）

回跳边（还有未完成项）：

```java
// SpEL，对 context.plan 求值。plan 是 List<Map>，判有没有 done==false 的项
plan.?[done == false].size() > 0
```

出环边（全部完成，作为 default 放最后，空表达式恒真）：

```java
// 空 condition_expr = 无条件恒真，排在 sort_no 最后 = else 分支（智能体设计 5.3）
```

> **转移裁决规则**（智能体设计 5.3）：按 `sort_no` 升序取**第一个 guard=true** 的边。所以
> 回跳边 `sort_no` 要小于 default 边。零匹配且非 TERMINAL → 实例 FAILED（这里因有 default 恒真边，
> 不会零匹配）。

### 2.4 "写入计划"到底写到哪（最关键的澄清）

**计划写进 `ExecutionContext`，不写数据库业务表。** 三层落库各归其位（迭代层第三章）：

| 落什么 | 谁落 | 时机 | 你要做的 |
|---|---|---|---|
| plan 数组本身 | 引擎自动（`node_result=context delta`） | 规划节点 SUCCESS 记账 | **什么都不用做**，outputKey 写 context 即自动落 |
| 每项执行产物 | 引擎自动（同上） | 执行节点每轮 SUCCESS | **什么都不用做** |
| 最终产物落业务库（如落进某张业务表） | 外层 Webhook 消费端 | 实例 terminal 后 | 配 `webhook.url`，走 [编排回调Webhook设计.md](./编排回调Webhook设计.md) |

> **为什么不能加"落库工具节点"写计划表**（迭代层 3.2 同款理由）：
> - 状态机中途成环，若执行节点后面回跳，中途插的计划表数据会脏；
> - 计划是 context 的一部分，崩溃恢复靠 `graph_snapshot + 增量重放`自动还原，另存表 = 双写不一致；
> - 铁律：**Agent 内部节点只写 context，绝不直连业务库**（智能体设计 三章铁律）。

### 2.5 恢复语义（自动获得，无需额外设计）

因为计划就是 context 数据，崩溃恢复完全复用智能体设计"四铁律"（二·3）：
- 从 `graph_snapshot` 载图 → 载 `context_snapshot` → 增量重放 `outcome=SUCCESS` 的 transition；
- 重放只**恢复 plan 和已完成项的产物**，**不重新调 LLM/工具**（不重复计费）；
- "做到第几项"天然记录在 context 的 `plan[].done` 里，恢复后从下一个 done=false 继续。

**这是"计划存 context"相对"计划存表"的最大优势：白拿了状态机的崩溃恢复能力。**

## 三、方案 C：跨天连载 = 迭代链，节点一个不改

如果你的"计划"是"生成大纲→每天基于大纲写一篇→边写边改大纲"这种**跨实例**递推，
[跨实例迭代层设计.md](./跨实例迭代层设计.md) 已**完整覆盖**，内核和节点一行不改：

- **大纲（计划）= 每轮实例的一个 output**（如 `context.outline`）；
- `carry_over` 把上轮 `outline` 映射成下轮 `inputs.outline`（迭代层 4.1）；
- **"边写边规划"= 每轮实例更新 outline 再写回 outputs**，下轮读到被改过的大纲（迭代层 2.1）；
- **"计划完成"= `until_expr`**（如 `outline.done == true`）判出链（迭代层 4 DDL）。

方案 A/B 与 C 可**叠加**：每一轮（C 的一天）内部，用 A/B 的成环 plan 结构写好这一篇。
即"外层迭代链管天级推进，内层状态机管单篇的计划-执行"。

## 四、可选：`PLAN` 节点（语法糖）——建议缓做

如果方案 B 被高频复用、且"每次都手写 `plan.?[done==false]` guard + 手搭三节点环"确实成为痛点，
可以把这套结构**封装成一个语义化 `PLAN` 节点**。

### 4.1 若要做，它长什么样

- **前端**（照 [ai-flow-frontend-only](../) 只落 `node.data.nodeConfig.plan`，不碰后端执行器）：
  新增 `PLAN` 节点类型，配置项：
  ```jsonc
  { "plan": {
      "plannerPrompt": "把目标拆成有序子任务，输出 JSON 数组",
      "planSchema": "[{id,step,tool,args,done}]",   // 计划项结构
      "executor": { "mode": "LLM|TOOL", "prompt/toolCode": "..." },  // 每项怎么执行
      "maxItems": 20                                  // 计划项上限（映射到 max_transitions 语义）
  } }
  ```
- **后端**：新增 `PlanNodeExecutor`，内部就是"LLM 生成 plan → 存 context → 驱动内嵌循环逐项执行"，
  等价于把第二章的三节点环封装进一个执行器（类比现有 `LOOP` 节点内嵌子图的做法，见 memory
  `ai-flow-loop-engine`）。

### 4.2 为什么建议缓做（对齐文档 4·5.4 拒绝阶段1做补偿的思路）

> 在本架构里，PLAN 节点能做的，`LLM + IF + 成环`已经能做，且**更透明**——每个子任务的执行
> 都是画布上一次独立的状态转移，**可单独回放、可单独重试、guard 可见**。把它塞进一个黑盒
> `PlanNodeExecutor`，反而丢掉状态机"每步转移可审计"的核心价值（智能体设计 4·5.3 重试落轨迹）。
>
> **建议路径**：先用第二章的组合节点跑通一个**真实 demo**，确认这个模式确实高频、且手写 guard
> 确实是痛点，再抽 PLAN 节点。过早封装 = 返工（智能体设计 4·5.4 同款判断）。

### 4.3 LOOP 节点 vs PLAN 节点的区别（避免混淆）

项目已有 `LOOP` 节点（memory `ai-flow-loop-engine`，FOREACH/COUNT 内嵌子图循环）。区别：

| | LOOP 节点 | 设想的 PLAN 节点 |
|---|---|---|
| 循环次数 | **编排时已知**（遍历固定集合 / 固定次数） | **运行时由 LLM 决定**（plan 长度动态） |
| 循环体 | 内嵌子图 | 单个执行策略 |
| 适用 | "对目录里每篇文章逐个处理" | "AI 拆出 N 个子任务逐个做" |

> 若你的计划项**数量运行时才知道**，LOOP 的 FOREACH 也能用（先让 LLM 生成 plan 数组写 context，
> 再用 LOOP FOREACH 遍历这个 context 数组）——**这可能比新造 PLAN 节点更省事**，值得优先验证。

## 五、决策建议（给评审）

1. **首选方案 A/B**：用 `LLM(规划,ENTRY) → 执行(LLM/TOOL) → IF(还有未完成项?) →回跳/终态` 的
   成环结构，`engine_type=STATE_MACHINE`。**零新节点**，计划存 context，白拿崩溃恢复。
2. **若跨天连载**：直接用迭代链（方案 C），可与 A/B 叠加（外层链 + 内层计划环）。
3. **PLAN 节点缓做**：先跑通真实 demo，验证痛点后再决定是否抽语法糖；且优先评估"LLM 生成 plan
   数组 + LOOP FOREACH 遍历"能否替代（第 4.3）。
4. **绝不做的事**：不建"计划表"、不加"落库计划的工具节点"（脏写 + 双写不一致 + 违反 context 铁律）。

## 六、完整形态落地（决策已定）

> 评审确认的目标形态：**跨天连载（C）的每一轮内部 = [规划 → 人工审批(真挂起) → ReAct 里程碑执行 → 产物落库]**，
> 外层迭代链驱动天级推进，产物经 Webhook 落进 blog 业务库。四项关键决策：
>
> | 决策点 | 选择 | 含义 |
> |---|---|---|
> | 时间尺度 | **C（跨天连载）+ 内层 B（单实例计划环）叠加** | 外层迭代链，内层状态机 |
> | 执行范式 | **分层混合** | 显式高层 plan 给人审批；里程碑内 ReAct 自主调工具 |
> | 人工介入 | **真挂起审批**（等待可能小时~天） | `stateConfig.suspend=true` + `signal` 唤醒 |
> | 产物消费 | **Webhook 回调落 blog** | 链级 `webhook_url`，草稿态入库 |

### 6.1 为什么必须"分层混合"（两个坑的解法）

评审暴露了两处直接冲突，分层混合是唯一自洽解：

**坑 1：纯 ReAct × 人工审批 自相矛盾。** 审批的前提是计划**显式可见**（审批人得看到"AI 打算做哪几步"），
而纯 ReAct 的计划是**隐式的、在模型脑子里的**，`context` 里没有可展示的 plan → 审批一个不存在的东西。
**解法**：先用一次 LLM 产出**显式高层 plan（里程碑级）** 给人审批 → approve → 每个里程碑内部再用
**ReAct loop** 自主调工具。审批显式层，执行自主层。

**坑 2：真挂起审批依赖阶段 3，是靠后的集成。** `SUSPENDED + signal` 是智能体设计阶段 3 能力；
完整形态实际需要 **阶段1内核 + 阶段2 Agent层 + 阶段3挂起 + 迭代层 + Webhook W1** 全部就位——
不是"一个新节点"能解决的（好在代码已基本就绪，见 6.4）。

### 6.2 分层混合完整图结构

```text
┌─ 外层：迭代链 ai_agent_iteration（天级，IterationDriver 定时推进）──────────────┐
│  cron 到点 → 读上轮 outputs.outline → carry_over 映射为本轮 inputs → 跑一轮实例  │
│  → advance 链 → Webhook POST 产物到 blog（advance 成功后触发，草稿态入库）        │
└────────────────────────────┬──────────────────────────────────────────────────┘
                             ▼ 每一轮 = 一个状态机实例（engine_type=STATE_MACHINE）
   [ENTRY] 规划节点 (LLM)
      │  prompt: "基于系列大纲/上轮产出，列出本篇的高层里程碑（3~6 步），输出 JSON 数组"
      │  outputKey: plan  → context.plan = [
      │                        {"id":1,"milestone":"调研本篇主题","done":false},
      │                        {"id":2,"milestone":"写初稿","done":false}, ...]
      ▼
   [审批节点] (LLM 或 NoOp)  ← stateConfig.suspend=true, awaitingEvents=[approve, revise]
      │  成功后主动挂起(SUSPENDED)，落库等 signal
      │  · signal(instanceId,"approve",{}) ─────────▶ guard 命中 → 进执行
      │  · signal(instanceId,"revise",{plan:[...]}) ─▶ guard 命中 → 回跳规划节点重列
      ▼
   [执行节点] (AgentReactNodeExecutor ★新增)
      │  取 plan 首个 done=false 里程碑
      │  用 DefaultToolCallingService.run(prompt, toolCodes, toolContext) 跑 ReAct loop：
      │      思考→选工具A→观察→思考→选工具B→…→里程碑完成
      │  标记该项 done=true；产物 + 工具轨迹写回 context（node_result delta）
      │  【动态追加】执行中可往 context.plan push 新里程碑（下一轮 IF 自动看到）
      ▼
   [IF] 还有未完成里程碑？
      ├─ guard: plan.?[done==false].size() > 0 ──────▶ 回跳「执行节点」（成环）
      └─ guard: 空(default，放最后) ──────────────────▶ [TERMINAL] 汇总 → outputs
                                                          （outline 更新也写进 outputs，供下轮 carry_over）
```

### 6.3 动态追加计划项如何落地（评审：需要）

- **里程碑内**：ReAct loop 天然支持——模型每轮自己决定下一步选哪个工具，无需额外设计。
- **高层 plan 层**：执行节点往 `context.plan` push 新里程碑，成环结构下一轮 IF 自动看到新项。
  **零成本**，成环结构天然覆盖"边做边发现要多做几步"。

### 6.4 阶段依赖清单（基于代码核实，非仅文档）

> 逐项核对后端代码后的 v2 结论：单实例计划环和 ReAct 执行器已具备；**跨实例链中的挂起轮次异步收口**、**动态多 Agent 委派**仍是独立待办，不能再表述为“只缺一个执行器”。

| # | 形态需要 | 对应能力 | 代码现状 | 结论 |
|---|---|---|---|---|

### 6.5 ReAct 里程碑执行器（`AgentReactNodeExecutor`）✅ 已编码

现有执行器都不满足"里程碑内自主调不同工具"：

- `PromptNodeExecutor` = **纯文本生成**，不接工具循环（代码核实：无任何 toolCalling 调用）。
- `ToolNodeExecutor` = **单工具**，`nodeConfig.toolCode` 固定调一个（代码核实：`resolveToolCode` 取单个 code）。
- `DefaultToolCallingService.run(request, toolCodes, toolContext)` = **能自主多工具循环**，但原**只被
  `AbstractAgent` 调用**，没有节点执行器把它接进状态机。

**已落地**：新增 `AgentReactNodeExecutor implements FlowNodeExecutor`（节点类型 `AGENT_REACT`），
`FlowAutoConfiguration` 注册为 Bean：
- 节点配置读 `nodeConfig.toolCodes`（字符串数组，模型可自选的工具集白名单）+ 提示词模板；
- 模型参数解析与 `PromptNodeExecutor` 同源（provider/model/temperature… 覆盖链）；
- 内部调 `toolCallingService.run(request, toolCodes, SimpleToolContext)` 跑 ReAct loop；
- 终轮文本按 `outputKey`（TEXT/JSON 模式）写回 context；`truncated=true`（达迭代上限）记 warn。

**已测试**：`AgentReactNodeExecutorTest`（12 例）+ `StubToolCallingService` 桩，`nebula-sdk-ai` 全量
**173 测试全绿**。测试同时把附录 A 依赖的两条契约钉成断言，防止后续改动悄悄破坏"计划环"：

| 测试 | 钉住的契约 | 为什么关键 |
|---|---|---|
| `渲染模板并把工具白名单透传给闭环` | `nodeConfig.toolCodes` → `ToolCallingService.run` 的 `allowedToolCodes` | 附录 A.1 ③ 执行节点的工具白名单真生效 |

```text

        / outputMode / outputKey / profileCode   ← ★后端读的模型与提示词
```

两份在同一次保存里同步写出，不会漂移；`normalizeAgentReactConfig` 在嵌套结构缺字段时会**回迁**
扁平契约，故手写 SQL 落的节点打开配置面板也能正确回显。**这让 `AGENT_REACT` 成为目前唯一一个
"画布配完即可直接运行"的节点** ——附录 A 的 `exec` 节点因此不用再手动补库。

> 字段同步即可（本次未动它，避免牵连回归）。

### 6.8 程序开发场景：计划项可以委派给多个 Worker Agent

`AgentReactNodeExecutor` 解决的是**一个 Agent 在一个里程碑内自主调用多个工具**。它不等于多个 Agent。对于“在对话框中同时调用后端程序员、前端程序员、测试和 Reviewer”的目标，执行节点应升级为 Lead Agent，并通过协作层工具委派：

```text
[ENTRY] 生成显式计划
   ↓
[人工审批]
   ↓
[Lead 执行/委派]
   ├── spawn_agent(java_coder, task A, worktree A)
   ├── spawn_agent(frontend_coder, task B, worktree B)
   └── wait_agents(ALL)
            ↓
       spawn_agent(test_agent, 集成后验证)
            ↓
       spawn_agent(review_agent, 只读审查)
   ↓
[IF] 是否仍有未完成/新增计划项？
   ├── 是 → 回跳 Lead 执行/委派
   └── 否 → [TERMINAL] 汇总
```

关键边界：

- 高层 `context.plan` 仍由状态机持有，是人工可见、可修改的控制计划。
- 每个委派项先成为可靠 `Agent Task`，再创建独立 Worker Instance。
- Lead 等待 Worker 时进入 `SUSPENDED`，不占用执行线程。
- 并行写 Worker 必须使用独立 worktree；最终 Test 必须在合并后的集成工作区运行。
- Worker 只返回结构化结果和产物引用，不把内部完整对话灌进 Lead Context。
- 父实例恢复后用 dispatchKey 找回原 Task，不重复 spawn。

完整的 Task 表、动态工具、父子终态事件和工作区设计见 [多智能体协作层设计.md](./多智能体协作层设计.md)。

## 附录 A：A 档骨架 —— 可直接照搬的配置值

> 以下所有字段名/键名/SpEL 写法均**经代码实证**（非文档推断）。可直接在画布搭建或落 `ai_flow_node`/`ai_flow_edge`。
>
> **关键实证结论（务必先读，避免踩坑）**：
> 1. **挂起配置**：`node_config.stateConfig.suspend=true` + `awaitingEvents:[...]`（`StateConfig.fromMap` 读这两个键）。
> 2. **事件大写归一化**：`AgentEngine.signal` 内部 `event.trim().toUpperCase()` 与 `awaitingEvents` 比对——
>    故 `awaitingEvents` 配**大写** `["APPROVE","REVISE"]`，唤醒时传的 event 也会被转大写。
> 3. **guard 根对象 = `OrchestrationContext`**（`ConditionCompiler`）：SpEL 里读上下文键用 **`get('键')`**，
>    读信号事件用 **`getString('__signalEvent')`**——**不能**写裸 `plan`（那样解析不到，且求值异常会抛错非静默 false）。
> 4. **signal 的 payload 直接展开进 context**（`payload.forEach(ctx::put)`）：故 `revise` 传 `{plan:[...]}` 会覆盖 `context.plan`。
> 5. **guard 求值失败会抛异常**（非静默 false）：对可能为 null 的键写**防御式**表达式（见下 IF 边写法）。

### A.0 前置：flow 用状态机内核

```jsonc
// ai_flow
{ "flowCode": "plan_exec_demo", "engineType": "STATE_MACHINE", "maxTransitions": 100 }
```

> `engineType=STATE_MACHINE` 才有回跳/成环/挂起；`maxTransitions` 兜底防死循环（计划里程碑很多时调大）。

### A.1 五个节点（`ai_flow_node`）

**① 规划节点（LLM，ENTRY）** —— 产出显式高层 plan 给人审批

```jsonc
{
  "nodeCode": "plan",
  "nodeType": "PROMPT",
  "stateType": "ENTRY",
  "systemPrompt": "你是资深内容规划师。把目标拆成 3~6 个高层里程碑。",
  "promptTemplate": "系列主题：{{topic}}\n已有大纲：{{outline}}\n请输出本篇的里程碑计划，严格返回 JSON：{\"plan\":[{\"id\":1,\"milestone\":\"...\",\"done\":false}], \"hasPending\":true}",
  "outputMode": "JSON",          // JSON 模式逐键展开：plan / hasPending 直接进 context
  "outputKey": "planRaw",
  "profileCode": "your_profile"
}
```

> JSON 模式下 `PromptNodeExecutor.writeOutput` 会把 `{plan, hasPending}` **逐键展开**进 context，
> 于是 `context.plan`、`context.hasPending` 可被后续 guard 直接读。让 LLM 一并产出 `hasPending` 布尔，
> **IF 判布尔比 SpEL 深入集合更稳**（见 A.3 两种 guard 写法）。

**② 审批节点（NoOp，成功后主动挂起）** —— 停下等人 approve/revise

```jsonc
{
  "nodeCode": "approve",
  "nodeType": "IF",              // 复用 NoOp 型；不产出，仅承载挂起 + 出边裁决
  "stateType": "NORMAL",
  "nodeConfig": {
    "stateConfig": {
      "suspend": true,                       // ★成功后主动挂起
      "awaitingEvents": ["APPROVE", "REVISE"] // ★大写；signal 的 event 必命中其一
    }
  }
}
```

> 审批节点用什么执行器都行（它只挂起不干活），这里用 `IF`（NoOp 型）最省——它有出边可承载 approve/revise 分流。
> 想在挂起前给审批人一段"计划说明"，把它换成 `PROMPT` 节点、prompt 里复述 plan 即可。

**③ 执行节点（AGENT_REACT）** —— 里程碑内自主调不同工具

```jsonc
{
  "nodeCode": "exec",
  "nodeType": "AGENT_REACT",     // ★B 档新增的执行器类型
  "stateType": "NORMAL",
  "systemPrompt": "你负责完成当前里程碑。可自主调用工具，完成后更新计划状态。",
  "promptTemplate": "全部里程碑：{{plan}}\n请完成第一个 done=false 的里程碑，产出结果；若发现需要新增里程碑，在返回里追加。严格返回 JSON：{\"plan\":[...更新后,完成项 done=true...], \"hasPending\": <还有未完成则 true>, \"articleBody\":\"...\"}",
  "outputMode": "JSON",
  "outputKey": "execRaw",
  "nodeConfig": {
    "toolCodes": ["search", "http_request"]  // ★模型可自选的工具白名单（对应 ToolDefinition.code()）
  },
  "profileCode": "your_profile"
}
```

> 执行节点每轮：读 `context.plan` → ReAct 自主调 `toolCodes` 里的工具完成首个未完成里程碑 →
> JSON 产出**更新后的 plan（完成项 done=true，可追加新项）** + `hasPending` + 业务产物 `articleBody`。
> 逐键展开后 `context.plan`/`context.hasPending` 被刷新，供下方 IF 判断。**动态追加**：模型在 plan 里加项即可。

**④ 判断节点（IF）** —— 成环控制

```jsonc
{ "nodeCode": "check", "nodeType": "IF", "stateType": "NORMAL" }
```

**⑤ 汇总节点（END/PROMPT，TERMINAL）**

```jsonc
{
  "nodeCode": "done",
  "nodeType": "END",
  "stateType": "TERMINAL",       // ★到达即实例 SUCCESS
  "nodeConfig": { "end": { "outputJson": "{\"outline\":\"{{outline}}\",\"articleBody\":\"{{articleBody}}\"}" } }
}
```

> END 节点按 `outputJson` 模板渲染最终 outputs——**这些 outputs 正是迭代链下一轮 carry_over 的数据源**，
> 也是 Webhook 送 blog 的 payload 来源。把 `outline`（更新后的大纲）放进去，实现"边写边规划"。

### A.2 边（`ai_flow_edge`，`conditionExpr` = SpEL，`sortNo` 升序取首个 true）

```jsonc
// 规划 → 审批
{ "fromNode": "plan",    "toNode": "approve", "conditionExpr": "",                                  "sortNo": 1 }

// 审批挂起唤醒后：approve → 执行 ；revise → 回跳规划（payload 里的新 plan 已覆盖 context）
{ "fromNode": "approve", "toNode": "exec",    "conditionExpr": "getString('__signalEvent') == 'APPROVE'", "sortNo": 1 }
{ "fromNode": "approve", "toNode": "plan",    "conditionExpr": "getString('__signalEvent') == 'REVISE'",  "sortNo": 2 }

// 执行 → 判断
{ "fromNode": "exec",    "toNode": "check",   "conditionExpr": "",                                  "sortNo": 1 }

// 判断：还有未完成 → 回跳执行（成环）；否则 → 终态（default 空表达式放最后）
{ "fromNode": "check",   "toNode": "exec",    "conditionExpr": "get('hasPending') == true",         "sortNo": 1 }
{ "fromNode": "check",   "toNode": "done",    "conditionExpr": "",                                  "sortNo": 2 }
```

> **注意 signal 事件比对用大写**（`== 'APPROVE'`）——因 `AgentEngine.signal` 已把入参 event 转大写写进
> `__signalEvent`（写入的是原始大小写，但 awaitingEvents 命中判断已大写化；为稳妥，唤醒时就传大写 `APPROVE`/`REVISE`，
> guard 按大写比对）。

### A.3 IF guard 两种写法（推荐判布尔）

```java
// ✅ 推荐：让 LLM 产出 hasPending 布尔，IF 只判布尔——简单、不依赖 plan 项内部结构
get('hasPending') == true

// ⚠️ 备选：SpEL 直接对 plan(List<Map>) 做选择投影——能用但更脆（plan 为 null 会抛异常）
get('plan') != null and get('plan').?[done == false].size() > 0
```

> 选布尔写法：执行节点已在 JSON 产出里带 `hasPending`，IF 判它即可，**避免 SpEL 深入集合易错**
> （对齐"guard 求值失败抛异常"的实证，防御成本更低）。

### A.4 唤醒审批（REST，阶段 4 已落地端点）

### A.5 迭代链配置（`ai_agent_iteration`，跨天连载 + Webhook）

```jsonc

  "agentCode": "plan_exec_agent",          // 指向引用了上面 flow 的 Agent（ai_agent.flowCode=plan_exec_demo）

  "carryOver": {                            // ★上轮 outputs 键 → 下轮 inputs 键
    "outline": "outline",                   // 更新后的大纲带给下一篇（边写边规划）
    "articleBody": "prevArticle"            // 上一篇正文（供本篇参考，建议只带摘要/oss key）
  },
  "seedInputs": {                           // ★首轮种子（第 0 轮无上一轮）
    "topic": "30 天 Java 进阶",
    "outline": ""
  },
  "webhookUrl": "http://blog-svc/admin/blog/webhook/series-append" // ★每轮 advance 成功后 POST 产物到 blog
}
```

> - **首轮**用 `seedInputs`（topic + 空 outline）启动；**后续轮**读上轮 outputs 按 `carryOver` 映射为 inputs。
> - `untilExpr` 对**上一轮产物**求值（同 SpEL 根对象规则，用 `get()`/`getString()`）。
> - `webhookUrl` 非空 → `IterationDriver` 在 `advance` **成功后**当场 POST 产物到 blog（[编排回调Webhook设计.md](./编排回调Webhook设计.md) 触发点①）。

### A.6 端到端数据流（一张图对齐所有配置）

```text
迭代链(cron 9点) ──seedInputs/carryOver──▶ inputs{topic,outline,prevArticle}
   │                                              ▼
   │   [plan] LLM 出 {plan,hasPending} ──▶ [approve] 挂起等 APPROVE/REVISE
   │                                              │ signal APPROVE
   │                                              ▼
   │   [exec] AGENT_REACT 调 toolCodes 完成里程碑，刷新 {plan,hasPending,articleBody}
   │                                              ▼
   │   [check] get('hasPending')==true? ─是→回跳 exec  └否→ [done] TERMINAL
   │                                                              ▼ outputs{outline,articleBody}
   └──advance 链(seq+1,next_run_at)──▶ Webhook POST outputs 到 blog(草稿入库)
                                        └ 下一轮 carryOver: outline→outline, articleBody→prevArticle
```

### A.7 落地方式：画布搭建（推荐）或手写 SQL

**B 档（执行器）与 C 档（前端节点）均已完成**，`exec` 节点现在有两种搭法：

- **画布搭建（推荐）**：左侧面板拖出「ReAct 执行」节点 → 右侧面板配模型档案 + 工具白名单（多选）+
  提示词 + 输出类型。配置弹窗会自动落出后端读取的扁平契约（见 6.7），**保存即可运行**。
- **手写 SQL**：按 A.1 ③ 的 JSON 直接落 `ai_flow_node`（`nodeType=AGENT_REACT`、`nodeConfig.toolCodes`
  + 顶层 `promptTemplate`/`outputMode` 等）。画布打开时会回迁回显，两种方式等价。

若要先验证全链路而不引入工具，可把 `exec` 降级为 `PROMPT`（纯 LLM 生成）或 `TOOL`（固定单工具），
**其余配置（挂起审批 + IF 成环 + 链 + webhook）完全不变**。工具白名单留空时 `AGENT_REACT` 本身也会
退化为纯对话（后端不报错），故直接用 `AGENT_REACT` 起步同样可行。
