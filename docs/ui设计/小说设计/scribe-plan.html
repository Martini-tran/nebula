一、书房 —— 打开应用看到的第一屏

这一屏只回答一个问题：我现在该写哪本、写到哪了。 所以顶部先给今日字数与连续天数（写作是习惯，这个数字比任何功能都更能让人坐下来）， 卡片上给进度条 + 未回收伏笔数——后者是提醒「这本书欠着读者三个交代」， 比「更新于 2 天前」有用得多。

二、大纲板 —— 在写之前先看见全书

为什么用看板而不是列表：写长篇最容易失控的不是文笔，是结构—— 十章草稿、三章修订、两章定稿散在目录树里，作者感觉不到「哪里堵住了」。 四列一字排开，堆积在哪一列一眼看得见。卡片可拖拽改状态，也可拖拽改顺序。 卡上标出这一章埋了/欠着哪些伏笔，让结构问题在写之前就暴露。

三、审校报告 —— 全书一致性检查的结果页

关键设计：规则检查与模型检查分开呈现。 「伏笔没回收」「关系生效章节颠倒」这类是规则算出来的，确定性 100%，不花 token； 「人物行为与设定冲突」是模型判的，可能误报。两者混在一个列表里， 用户就会用对待误报的态度对待所有条目，确定性高的那部分反而被忽略。 所以分组、标注来源，并且规则组永远排在前面。

四、三块原型的关系

书房（本页一）→ 选一本书 → 大纲板（本页二）看结构、写作台 （scribe-editor.html）写正文、故事世界（scribe-world.html）管人物与编年 → 写完跑审校报告（本页三）。

三块共用同一套令牌、同一套「AI 只提议不静默改」的交互律、同一套出处链接（章节 + 段落）。 后端设计见 docs/写作Agent设计.md。
