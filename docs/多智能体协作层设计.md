# nebula 多智能体协作层设计 v1

> 本文档是 [智能体设计.md](./智能体设计.md) 的协作层增补，定义如何在稳定的 Agent Runtime 之上，由对话中的主智能体按需创建、等待、取消并汇总多个专业子智能体。
>
> 核心定位：**nebula 不是一个不断膨胀的单体 Agent，而是一个可持久化、可恢复的 Agent Runtime；一次对话由一个 Lead Agent 负责目标，多名 Worker Agent 以独立实例完成子任务。**

---

## 〇、先统一四个概念

| 概念 | 含义 | 是否长期存在 |
|---|---|---|
| **Agent Runtime** | 状态机/DAG、实例持久化、恢复、记忆、工具治理、迭代链等运行基础设施 | 是 |
| **Agent Definition** | 一个智能体的静态定义，如 Lead、Java Coder、Reviewer；对应 `ai_agent` | 是，按版本发布 |
| **Agent Task** | 父智能体委派给子智能体的一项工作及其完成条件，是协作层的可靠任务信封 | 是，保留审计 |
| **Agent Instance** | 某个 Agent Definition 为完成一次 Task 而产生的一次执行；对应 `ai_agent_instance` | 是，保留回放 |

因此：

- 一个系统可以只有一套 Runtime，却注册很多 Agent Definition。
- 同一个 Agent Definition 可以同时创建多个 Agent Instance。
- “调用了多次 LLM/工具”不等于多智能体；只有当执行单元拥有独立上下文、生命周期、权限和结果契约时，才是子智能体。
- Conversation/Thread 是用户交互容器，不等于 Agent；它通常绑定一个 Lead Agent Instance。

---

## 一、目标与非目标

### 1.1 目标

1. 对话中的 Lead Agent 能根据任务动态决定是否委派、委派给谁、并行几个。
2. Worker Agent 拥有独立 Context、Memory Import、工具权限、状态和终态结果。
3. 父进程崩溃、父/子实例挂起或服务重启后，协作关系仍可恢复。
4. 多个 Coding Agent 修改代码时有工作区隔离、写范围约束和可控合并。
5. 所有 spawn/wait/cancel/collect 行为可审计、可重放且不会因恢复重复创建子实例。
6. 保留现有 `AgentNodeExecutor` 的静态子流程能力，同时新增运行时动态协作能力。

### 1.2 非目标

- 阶段 1 不做子 Agent 之间的自由对话网络，统一由 Lead Agent 调度。
- 阶段 1 不做自治组织、角色投票、无限自繁殖等开放式群体行为。
- 不让多个写 Agent 直接并发修改同一个工作目录。
- 不承诺 exactly-once；创建子任务、工具副作用和合并操作都依赖幂等键实现业务去重。
- 不把协作状态塞进长期 Memory；Task/Instance/Workspace 都有自己的强一致持久化记录。

## 二、总体架构：稳定运行时 + 主从式多智能体

```text
Conversation / Thread
        │
        ▼
Lead Agent Instance（稳定目标持有者）
        │
        ├── list_agents() / spawn_agent()
        │          │
        │          ├── Agent Task A → Java Coder Instance ── Workspace A
        │          ├── Agent Task B → Frontend Coder Instance ─ Workspace B
        │          └── Agent Task C → Reviewer Instance ───── Read-only View
        │
        ├── wait_agents(ALL | ANY | QUORUM)
        ├── send_message() / cancel_agent()
        └── collect_results() → 汇总、冲突处理、最终验证
```

职责边界：

| 层 | 负责 | 不负责 |
|---|---|---|
| **Agent Runtime** | 可靠执行、恢复、转移、实例版本锁定 | 决定业务上该找哪个 Worker |
| **Lead Agent** | 拆任务、依赖排序、选择 Worker、汇总结果 | 直接管理线程、数据库锁和工作区进程 |
| **Agent Collaboration Service** | Task 持久化、spawn 幂等、等待/取消、父子唤醒 | 推理任务内容 |
| **Worker Agent** | 在限定上下文和工具内完成一个子任务 | 修改父 Context/Memory、直接推进迭代链 |
| **Workspace Service** | worktree/sandbox 创建、权限、Diff、合并、清理 | 评价代码业务正确性 |

## 三、两种子 Agent 调用必须并存

### 3.1 静态调用：`AgentNodeExecutor`

Flow 在设计时已确定子 Agent，适合稳定业务流程：

```text
[规划] → [AGENT: 风控审核] → [人工审批] → [执行]
```

特点：

- 子 Agent 类型和位置在 Flow 图中固定。
- Input/Output Mapping 在发布时确定。
- 适合审批、风控、订单处理等结构稳定的编排。

### 3.2 动态调用：Sub-Agent Runtime Tools

Lead Agent 在运行时根据任务动态决定 Worker 数量和类型，适合程序开发、研究、诊断等开放任务：

```text
用户：完成前后端接口并补测试
Lead：识别为三个可分离子任务
  ├── spawn Java Coder
  ├── spawn Frontend Coder
  └── 两者完成后 spawn Test/Review Agent
```

**决策**：动态协作不新增一种编排内核；它作为受治理的工具集接入 Lead Agent 的 ReAct loop。每次 `spawn_agent` 内部仍调用现有 `AgentEngine` 创建标准实例。

### 3.3 Lead/Worker 协作配置

协作权限属于 Agent Definition 版本的一部分，落 `ai_agent.collaboration_config`：

```jsonc
{
  "canDelegate": true,
  "allowedWorkerAgents": ["java_coder", "frontend_coder", "test_agent", "review_agent"],
  "maxChildrenPerInstance": 8,
  "maxTotalTasksPerRoot": 24,
  "maxParallelTasksPerRoot": 4,
  "maxDelegationDepth": 3,
  "maxTokenBudgetPerTask": 120000,
  "maxCostBudgetPerRoot": 20.0
}
```

- Lead 只能看到白名单内已启用、输入契约兼容的 Worker。
- Worker 不继承 Lead 权限；只有自己的 `canDelegate=true` 才能继续 spawn。
- 配置随 Agent 版本锁定，运行中的协作树不会因后台修改白名单而漂移。

## 四、Sub-Agent Runtime Tool 契约

仅具备 `canDelegate=true` 权限的 Agent 可见以下工具。

### 4.1 `list_agents`

按当前 Lead Agent 的允许列表返回可委派 Agent，不向模型暴露全平台 Agent：

```jsonc
{
  "agents": [
    {
      "agentCode": "java_coder",
      "description": "实现和修改 Java/Spring 代码",
      "inputSchema": {},
      "outputSchema": {},
      "capabilities": ["java", "spring", "test"],
      "workspaceMode": "WORKTREE"
    }
  ]
}
```

### 4.2 `spawn_agent`

```jsonc
{
  "agentCode": "java_coder",
  "task": {
    "title": "实现订单状态接口",
    "instruction": "按现有 Service/Controller 模式实现并补单测",
    "completionCondition": "模块编译通过且相关测试通过"
  },
  "input": {
    "repository": "nebula",
    "baseRef": "working-tree",
    "contextRefs": ["docs/order-api.md"]
  },
  "workspace": {
    "mode": "WORKTREE",
    "writeScope": ["nebula-service-order/**"],
    "readScope": ["nebula-service-order/**", "nebula-common/**"]
  },
  "dispatchKey": "order-status-backend-v1"
}
```

返回：

```json
{
  "taskId": "task-xxx",
  "instanceId": "java_coder-xxx",
  "status": "RUNNING",
  "workspaceId": "ws-xxx"
}
```

`dispatchKey` 是父实例当前委派意图中的稳定键。服务端幂等键为：

```text
parentInstanceId + parentState + dispatchKey
```

父实例在 `spawn_agent` 成功后、状态转移落账前崩溃并重放时，再次调用相同 dispatchKey 必须返回原 Task/Instance，绝不重复创建 Worker。

### 4.3 `wait_agents`

```jsonc
{
  "taskIds": ["task-a", "task-b"],
  "policy": "ALL",          // ALL | ANY | QUORUM
  "quorum": null,
  "timeoutMs": 3600000
}
```

等待不是阻塞 Java 线程：

- 条件未满足时，父实例置 `SUSPENDED`。
- `awaiting_events` 写入内部事件，如 `AGENT_TASK_TERMINATED:task-a`。
- 子任务终态事件到达后，协作服务按 CAS 唤醒父实例。
- `ALL` 在全部终态后唤醒；`ANY` 首个终态即唤醒；`QUORUM` 达指定数量后唤醒。

### 4.4 `send_message`

只允许给当前父实例创建的非终态 Task 追加指令。消息作为 Task event 落库，再由 Worker 在安全检查点读取；不直接修改正在执行方法的内存对象。

### 4.5 `cancel_agent`

取消语义分两层：

- `CANCEL_REQUESTED`：已记录取消请求，等待 Worker 到安全检查点停止。
- `CANCELLED`：Worker 已停止并落终态。

不使用强杀线程作为正常取消机制；外部工具调用能否终止由 Provider 能力决定。

### 4.6 `collect_results`

只从 Task/Instance 的终态快照读取，不重新执行 Worker：

```jsonc
{
  "results": [
    {
      "taskId": "task-a",
      "status": "SUCCESS",
      "summary": "已完成订单状态接口",
      "artifacts": [{"type":"PATCH","key":"oss://..."}],
      "filesChanged": ["OrderController.java"],
      "tests": [{"command":"mvn -pl ... test","status":"PASSED"}],
      "findings": [],
      "proposedMemoryChanges": []
    }
  ]
}
```

## 五、可靠任务模型：新增 `ai_agent_task`

`Agent Instance` 表达“一次怎么执行”，`Agent Task` 表达“父 Agent 委派了什么工作”。二者不能混为一张表：Task 需要等待策略、工作区、完成条件、取消和结果信封；Instance 需要状态机当前状态、图快照和转移历史。

```sql
CREATE TABLE ai_agent_task (
  id                    BIGINT       PRIMARY KEY AUTO_INCREMENT,
  task_id               VARCHAR(64)  NOT NULL COMMENT '任务业务标识',
  root_instance_id      VARCHAR(64)  NOT NULL COMMENT '本次协作树的 Lead 根实例',
  parent_instance_id    VARCHAR(64)  NOT NULL COMMENT '发起委派的父实例',
  parent_state          VARCHAR(64)  NOT NULL COMMENT '父实例在哪个状态发起委派',
  parent_task_id        VARCHAR(64)           COMMENT '多层委派时的父任务',
  agent_code            VARCHAR(64)  NOT NULL,
  agent_version         INT          NOT NULL COMMENT '创建时锁定的 Agent 版本',
  instance_id           VARCHAR(64)           COMMENT '承载本任务的 Agent Instance',
  title                 VARCHAR(256) NOT NULL,
  task_spec             TEXT         NOT NULL COMMENT 'instruction/input/completionCondition JSON',
  result_schema         TEXT                  COMMENT '结构化结果契约 JSON Schema',
  result                TEXT                  COMMENT '终态结果信封 JSON',
  depends_on            TEXT                  COMMENT '前置 taskId 数组 JSON；全部成功后才可调度',
  priority              INT          NOT NULL DEFAULT 0,
  workspace_id          VARCHAR(64),
  dispatch_key          VARCHAR(128) NOT NULL COMMENT '父实例内稳定委派键',
  status                VARCHAR(24)  NOT NULL COMMENT 'PENDING|RUNNING|WAITING|SUCCESS|FAILED|CANCEL_REQUESTED|CANCELLED',
  status_version        INT          NOT NULL DEFAULT 0 COMMENT '状态事件版本，终态通知幂等依据',
  error_msg             TEXT,
  lock_version          INT          NOT NULL DEFAULT 0,
  create_time           DATETIME,
  update_time           DATETIME,
  UNIQUE KEY uk_task_id (task_id),
  UNIQUE KEY uk_parent_dispatch (parent_instance_id, parent_state, dispatch_key),
  UNIQUE KEY uk_instance_id (instance_id),
  KEY idx_root_status (root_instance_id, status),
  KEY idx_parent_status (parent_instance_id, status)
) COMMENT='Agent 间可靠委派任务';
```

### 5.1 为什么 Task 锁定 Agent 版本

`spawn_agent` 创建 Task 时解析“当前允许使用的 Agent 版本”，立即写入 `agent_version`；随后创建的 Instance 只能使用该版本。Task 等待期间即使 Worker Agent 发布新版，也不会漂移。

### 5.2 Task 与 Instance 状态关系

| Instance 状态 | Task 状态 | 说明 |
|---|---|---|
| 尚未创建 | PENDING | 等待并发配额/工作区 |
| RUNNING | RUNNING | 正常执行 |
| SUSPENDED | WAITING | 等人工、工具或子任务事件 |
| SUCCESS | SUCCESS | 固化 result 后发布终态事件 |
| FAILED | FAILED | 保留错误和可重试依据 |
| 任意非终态 + 取消请求 | CANCEL_REQUESTED | 等待安全停止 |
| 已停止 | CANCELLED | 终态 |

Task 终态写入与“待发布终态事件”必须位于同一事务，推荐本地 Outbox；事件投递至少一次，消费者按 `taskId + statusVersion` 幂等。

### 5.3 Task Event：消息、取消与审计日志

`send_message`、人工追加约束和取消请求需要独立持久化，不能只修改当前内存 Context：

```sql
CREATE TABLE ai_agent_task_event (
  id              BIGINT       PRIMARY KEY AUTO_INCREMENT,
  event_id        VARCHAR(64)  NOT NULL,
  task_id         VARCHAR(64)  NOT NULL,
  event_type      VARCHAR(32)  NOT NULL COMMENT 'MESSAGE|CANCEL_REQUESTED|PROGRESS|NOTE',
  source_type     VARCHAR(16)  NOT NULL COMMENT 'USER|LEAD|WORKER|SYSTEM',
  source_id       VARCHAR(64),
  payload         TEXT         NOT NULL,
  status          VARCHAR(16)  NOT NULL DEFAULT 'PENDING' COMMENT 'PENDING|CONSUMED|IGNORED',
  consumed_at     DATETIME,
  create_time     DATETIME,
  UNIQUE KEY uk_event_id (event_id),
  KEY idx_task_status (task_id, status, id)
) COMMENT='Agent Task 指令/进度事件日志';
```

- MESSAGE 由 Worker 在安全检查点按 id 顺序消费，消费后记录 `CONSUMED`。
- CANCEL_REQUESTED 同时 CAS Task 状态，Event 用于执行器感知和审计。
- PROGRESS/NOTE 可供界面展示，但不作为任务完成的权威状态。
- 已进入终态的 Task 拒绝新的 MESSAGE；重复 eventId 幂等返回原记录。

### 5.4 内部生命周期 Outbox

父子唤醒、迭代轮次收口属于运行时正确性，不能用内存 Listener，也不能复用对外 Webhook Delivery。新增通用内部 Outbox：

```sql
CREATE TABLE ai_agent_event_outbox (
  id              BIGINT       PRIMARY KEY AUTO_INCREMENT,
  event_id        VARCHAR(64)  NOT NULL,
  aggregate_type  VARCHAR(32)  NOT NULL COMMENT 'AGENT_INSTANCE|AGENT_TASK|ITERATION_RUN',
  aggregate_id    VARCHAR(64)  NOT NULL,
  aggregate_version INT        NOT NULL COMMENT '来源状态版本',
  event_type      VARCHAR(64)  NOT NULL COMMENT 'INSTANCE_SUSPENDED|INSTANCE_TERMINATED|TASK_TERMINATED|...',
  payload         TEXT         NOT NULL,
  status          VARCHAR(16)  NOT NULL DEFAULT 'PENDING' COMMENT 'PENDING|PROCESSING|SUCCESS|FAILED|DEAD',
  attempts        INT          NOT NULL DEFAULT 0,
  next_retry_at   DATETIME,
  create_time     DATETIME,
  update_time     DATETIME,
  UNIQUE KEY uk_event_id (event_id),
  UNIQUE KEY uk_aggregate_event (aggregate_type, aggregate_id, aggregate_version, event_type),
  KEY idx_dispatch (status, next_retry_at)
) COMMENT='Agent Runtime 内部生命周期事件 Outbox';
```

规则：

1. 聚合状态更新与 Outbox INSERT 在同一数据库事务。
2. Dispatcher 至少一次投递；失败指数退避，达上限 DEAD 并告警。
3. 消费者不以“是否收到过”作为正确性，而是用目标记录状态/版本 CAS 幂等处理。
4. Outbox payload 只存标识、状态和必要结果引用，不复制完整 Context 或文件内容。
5. 外部 Webhook 在内部状态完成后触发，两套投递表和重试策略互不替代。

## 六、父子实例异步编织

现有 `parent_instance_id` / `parent_node_code` 只能建立实例树，还不足以完成异步生命周期。完整规则如下。

### 6.1 子挂起

```text
Worker Instance → SUSPENDED
  ↓ 同事务/可靠事件
Agent Task → WAITING
  ↓
父实例是否等待，由 wait_agents 的 policy 决定
```

子挂起本身不自动判父失败，也不要求父同步阻塞。

### 6.2 子完成

```text
Worker Instance → SUCCESS/FAILED/CANCELLED
  ↓
固化 Task.result + Task 终态
  ↓
发布 AGENT_TASK_TERMINATED(taskId, statusVersion)
  ↓
Wait Coordinator 重新计算 ALL/ANY/QUORUM
  ↓ 条件满足
CAS signal 父实例并恢复
```

### 6.3 父恢复幂等

父实例恢复到委派状态时：

1. 按 `(parent_instance_id, parent_state, dispatch_key)` 查询 Task。
2. 已存在则复用，禁止重建 Worker。
3. Task 非终态则重新挂接等待事件。
4. Task 已终态则读取 result 并继续，不重新执行 Worker。

### 6.4 父取消/失败

默认策略：

- 父 `FAILED/CANCELLED` 时，对仍由其独占的子 Task 发 `CANCEL_REQUESTED`。
- 已被其它父任务引用的共享 Task 不级联取消（阶段 1 不支持共享 Task，因此默认全部级联）。
- 父 SUCCESS 后不允许仍有未处理的非终态子 Task；编图/终态校验发现则拒绝结束或按策略取消。

## 七、Context 与 Memory 隔离

### 7.1 Context 传递

父 Agent 只通过 `task_spec.input` 和引用列表向 Worker 传数据，不共享可变 Context Map：

```text
Parent Context --Input Mapping/Task Spec--> Child Inputs
Parent Context <--Task Result Envelope------- Child Outputs
```

Worker 的内部 Messages、工具轨迹和临时变量不进入父对话，只把结构化结果、产物引用和必要摘要返回。

### 7.2 Memory 规则

- Lead Agent 持有用户偏好、项目约定和协作历史等长期记忆。
- Worker 默认只 Import 自己 Agent Code 下的专业记忆以及父任务显式提供的项目快照。
- Worker 不直接修改 Lead Agent Memory。
- Worker 可在结果中返回 `proposedMemoryChanges`，由 Lead 或专门的 Memory Curator 审核后写入。
- 同一 Worker Definition 的并行实例仍遵守现有“运行期只写 Context，终态统一 Export”规则。

## 八、程序开发工作区模型

### 8.1 隔离模式

| 模式 | 适用 | 写权限 |
|---|---|---|
| `READ_ONLY` | Review、分析、测试报告 | 禁止写 |
| `SHARED_READ` | 读取当前工作区但不修改 | 禁止写 |
| `WORKTREE` | 并行 Coding Agent | 独立 Git worktree 可写 |
| `SANDBOX` | 执行不可信代码/脚本 | 容器或隔离执行环境 |

**阶段 1 决策**：每个并行写 Worker 必须使用独立 worktree；禁止两个活跃 Task 共享同一可写目录。

### 8.2 新增 `ai_agent_workspace`

```sql
CREATE TABLE ai_agent_workspace (
  id                BIGINT       PRIMARY KEY AUTO_INCREMENT,
  workspace_id      VARCHAR(64)  NOT NULL,
  root_instance_id  VARCHAR(64)  NOT NULL,
  repository        VARCHAR(256) NOT NULL,
  base_ref          VARCHAR(256) NOT NULL,
  provider          VARCHAR(32)  NOT NULL COMMENT 'LOCAL_WORKTREE|CONTAINER|REMOTE',
  provider_ref      VARCHAR(512)          COMMENT 'READY 后写入的工作区提供者内部引用，禁止存凭据',
  write_scope       TEXT                  COMMENT '允许写路径 JSON',
  status            VARCHAR(24)  NOT NULL COMMENT 'CREATING|READY|IN_USE|MERGING|MERGED|CONFLICT|RELEASED',
  lock_version      INT          NOT NULL DEFAULT 0,
  create_time       DATETIME,
  update_time       DATETIME,
  UNIQUE KEY uk_workspace_id (workspace_id),
  KEY idx_root_status (root_instance_id, status)
) COMMENT='Agent 代码工作区';
```

`provider_ref` 是工作区引用，不应假定所有节点都能访问某个本地绝对路径；多实例部署时由 Workspace Provider 解析。

### 8.3 写范围与合并

- `writeScope` 在任务创建时声明，工具层对越界写入直接拒绝。
- Worker 返回 `filesChanged` 和 Patch/Commit 引用，不直接合并主工作区。
- Lead/Integration Agent 按依赖顺序合并。
- 合并冲突产生新的 Conflict Resolution Task，不让原 Worker 在未知新基线上静默重写。
- 最终 Test Agent 必须在合并后的集成工作区验证，子 worktree 中通过不代表整体通过。

## 九、并行与依赖

Lead Agent 可以动态创建任务 DAG，但状态机内核本身仍保持单点推进：

```text
Lead 状态机
   ↓ spawn A/B/C
Agent Task DAG
   ├── A ─┐
   ├── B ─┼── wait ALL → Integration → Test → Review
   └── C ─┘
   ↓
Lead 状态机恢复
```

### 9.1 并行条件

仅当以下条件同时满足时并行：

- 任务之间没有显式依赖。
- 可写路径不重叠，或全部只读。
- 全局、用户、Conversation 和 Agent 并发配额允许。
- Worker 所需工具和 Sandbox 资源可用。

否则 Lead 应串行执行，或先拆出公共前置任务。

### 9.2 限额

至少支持：

- `maxChildrenPerInstance`
- `maxTotalTasksPerRoot`
- `maxParallelTasksPerRoot`
- `maxDelegationDepth`
- `maxTaskDuration`
- `maxTokenBudgetPerTask`
- `maxCostBudgetPerRoot`

达到上限不是普通工具错误，应返回结构化 `LIMIT_REACHED`，由 Lead 重新规划或请求人工决策。

## 十、失败与恢复语义

| 故障点 | 恢复行为 |
|---|---|
| spawn 创建 Task 后、父转移落账前崩溃 | 用 parent+state+dispatchKey 找回原 Task，不重复创建 |
| Task 已建、Instance 未建时崩溃 | 调度器扫描 PENDING Task 创建 Instance |
| Worker RUNNING 时进程崩溃 | 走现有 AgentEngine resume 四铁律 |
| Worker 完成、父未收到事件时崩溃 | Outbox 重投终态事件，父按状态版本幂等消费 |
| 父恢复时 Worker 尚未完成 | 重新建立 awaiting_events，不阻塞线程 |
| wait ANY 后其它 Worker 仍运行 | 按配置 KEEP_RUNNING 或 CANCEL_REMAINDER |
| 工作区创建失败 | Task FAILED，不创建 Agent Instance |
| 合并冲突 | Workspace=CONFLICT，创建冲突解决 Task |

**副作用边界不变**：状态机和协作层均为 at-least-once。外部工具、Git 合并、发布、发消息等必须使用 `taskId + operationKey` 作为幂等键。

## 十一、安全与治理

1. Lead 只能委派 `allowedWorkerAgents` 白名单中的 Agent。
2. Worker 不能天然获得 Lead 的全部工具，按 Agent Definition + Task Scope 取交集。
3. Secret 只以引用注入工具执行环境，不进入 Task Spec、Context Snapshot、Transition 或 Result。
4. Sandbox 禁止默认访问宿主文件系统、Docker Socket 和内网地址。
5. 高风险工具可要求 Human-in-the-loop 审批，审批对象必须包含工具名、参数摘要和目标资源。
6. 所有委派、取消、消息、合并和人工审批记录审计人/来源/时间。
7. 防 Prompt Injection：来自仓库、网页和子 Agent 的文本都视为不可信数据，不能扩大 Worker 权限。

## 十三、与现有设计的关系

| 现有能力 | 本设计如何复用/补齐 |
|---|---|
| `AgentEngine` | Worker Instance 的统一创建、执行、挂起、恢复入口 |
| `AgentNodeExecutor` | 保留静态子 Agent 调用；异步挂起编织改由 Collaboration Service 完成 |
| `AgentReactNodeExecutor` | Lead 可在 ReAct loop 中调用 Sub-Agent Runtime Tools |
| `ai_agent_instance` | 保存每个 Lead/Worker 的执行状态与父子实例树 |
| `ai_agent_task` | 新增，保存动态委派意图、幂等键、等待和结果信封 |
| `ai_agent_task_event` | 新增，保存消息、取消、进度和人工追加指令 |
| `ai_agent_event_outbox` | 新增，可靠传递实例/任务内部生命周期事件 |
| `ai_agent_iteration` | 跨时间推进根任务；一轮内部可使用本设计的多 Agent 协作 |
| Webhook Delivery | 只负责对外投递，不承担父子实例内部唤醒 |
| Memory Import/Export | 每个 Agent 独立执行；Lead 统一决定跨 Agent 记忆沉淀 |

内部父子唤醒与外部 Webhook 必须分开：前者是运行时正确性的一部分，要求持久化事件/Outbox；后者是业务产物通知，失败不翻实例终态。

## 十四、落地路线

### 阶段 M1：可靠委派最小闭环

- `ai_agent_task` + store
- `ai_agent_task_event` + 安全检查点消费
- `ai_agent_event_outbox` + Dispatcher
- `list_agents` / `spawn_agent` / `wait_agents` / `collect_results`
- spawn 幂等键
- 单父多子实例树
- 子终态事件唤醒父实例
- 先只支持串行和 wait ALL

### 阶段 M2：程序开发工作区

- Workspace Provider SPI
- Git worktree 隔离
- read/write scope
- Diff/Commit 结果信封
- Integration + Test 收口

### 阶段 M3：并行、取消与治理

- 并行配额与 Task 依赖
- wait ANY/QUORUM
- cancel/timeout/budget
- 工具风险等级和审批
- Sandbox Provider

### 阶段 M4：可观测与评测

- Lead/Task/Worker Trace 树
- Token、成本、延迟、失败类型
- 版本对比和回归评测
- 工作区冲突率、人工介入率、恢复成功率指标

## 十五、决策记录

- ✅ **一套 Runtime，多份 Agent Definition，多次 Agent Instance**；不把平台本身叫作单个 Agent。
- ✅ **Lead-Worker 主从模型优先**；阶段 1 不做 Worker 间自由对话。
- ✅ **静态 AgentNode 与动态 Sub-Agent Tools 并存**，分别服务稳定流程和开放任务。
- ✅ **新增 Agent Task**，把委派意图与执行实例分离。
- ✅ **spawn 必须幂等**，键为 parentInstanceId + parentState + dispatchKey。
- ✅ **等待通过 SUSPENDED + 持久化终态事件实现**，不阻塞 Java 线程。
- ✅ **父子内部唤醒不走 Webhook**；Webhook 只用于系统外业务投递。
- ✅ **Lead 持有目标与汇总权，Worker Context/Memory 默认隔离**。
- ✅ **并行写 Agent 必须独立 worktree/sandbox**，最终在集成工作区统一测试。
- ✅ **状态机保持串行控制，Task DAG 提供并行执行**，不重写状态机内核。
- ✅ **协作层仍是 at-least-once**，所有外部副作用必须自带幂等键。
