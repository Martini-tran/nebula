# nebula 智能体架构设计（修订版 v4）

> 术语：本文档旧稿曾用 "Ganet" 作为 Agent 子系统的内部代号，现统一为 nebula。

> 本版在 v1 理念的基础上，**对齐 nebula 后端已落地的 AI 编排能力**，并补齐多智能体边界（完整清单见第十四章）。核心五项：
>
> 1. 执行语义 = **真·状态机**（节点可回跳、可成环、可等待外部事件）。
> 2. **Agent 独立建表**（`ai_agent`），Flow 保持纯编排结构，一个 Flow 可被多个 Agent 复用。
> 3. 状态机内核 **新建 `StateMachineOrchestrator`，与现有 `DagOrchestrator` 并存**，由 Flow 定义上的 `engine_type` 选择。
> 4. 本文档为落地依据，代码分阶段实现（见 第十二章 · 落地路线）。
> 5. **Agent Runtime 与 Agent Definition/Task/Instance 分离**：一套稳定运行时承载多个 Agent；动态协作由独立的多智能体协作层负责。

## 〇、与现有后端的关系（先读这一章）

nebula 后端**已经建好了本设计所需的大部分砖块**，本设计不是从零开始，而是"补齐缺口 + 引入状态机内核 + 用 Agent 层收口"。现状对照：

| 本设计概念 | 后端现状 | 处理方式 |
|---|---|---|
| Agent Definition（静态定义） | `AiFlow` + `AiFlowNode` + `AiFlowEdge`（`nebula-sdk-ai-flow`） | **保留**，作为 Agent 引用的"编排图"；Agent 层新增 |
| Agent Instance（一次执行） | `AiFlowRun` + `AiFlowRunNode` + `RunSnapshot` + 续跑 | **DAG 版续跑保留**；状态机版**另建实例表**（见 第七章） |
| Agent Task（父子委派） | 无 | 动态多智能体协作新增 `ai_agent_task`；与 Instance 分离，保存委派意图、幂等键、等待和结果信封 |
| Execution Context | `OrchestrationContext`（黑板，`attributes`+`nodeResults`） | **扩展**为分区上下文（Inputs/Variables/Messages/Artifacts/Outputs/Local Memory/Metadata） |
| Agent Memory（长期） | `AgentMemory` + `DatabaseLongTermMemory` + `ai_memory` 表 | **保留**，新增 Import/Export 钩子接入执行生命周期 |
| Agent 身份 | `com.nebula.common.ai.agent.Agent`（`agentCode`+`memory`） | **复用/演进**为运行时 Agent 门面 |
| 编排内核 | `DagOrchestrator`（有向无环，入度归零推进） | **并存**，新增 `StateMachineOrchestrator` |
| 工具调用 | `DefaultToolCallingService`（function-calling loop + 治理） | **直接复用** |
| 模型档案 / MCP / 工具 | `ai_model_profile` / `ai_mcp_server` / `ai_tool` | **直接复用** |

> 一句话：**Flow 系（编排结构）已就绪，本设计在其上加 Agent 层、换状态机内核、补 Memory 生命周期钩子。**

## 一、设计理念

nebula 既不是单纯的 Workflow 平台，也不是单纯的 Agent 框架。核心理念：

> **Workflow 是 Agent，Agent 也是 Workflow。**

这里的“Agent”指可发布、可执行的 Agent Definition；nebula 平台本身是 **Agent Runtime**，不应被描述成一个无限膨胀的单体 Agent。一套 Runtime 可以注册多个 Definition，一次对话由一个 Lead Agent Instance 按需创建多个 Worker Agent Instance。静态递归和动态协作的边界见第六章及 [多智能体协作层设计.md](./多智能体协作层设计.md)。

一个 Flow 中的 **Agent 节点** 既可以直接调 LLM，也可以引用另一个 Flow（子 Agent），因此系统天然支持递归。

```text
Agent A（引用 Flow A）
│
├── LLM 节点
├── Tool 节点
├── Agent 节点 → Agent B（引用 Flow B）
│                 ├── Tool 节点
│                 ├── LLM 节点
│                 └── Agent 节点 → Agent C
└── End 节点
```

**修订点**：v1 说"整个框架只有一种执行模型"。修订版明确：执行模型有 **两种内核**（DAG / 状态机），由 Flow 的 `engine_type` 选择，但**对上层 Agent 透明** —— Agent 只关心"跑一个 Flow，进→出→记忆"，不关心内核。

## 二、核心对象

```text
Agent Definition   ← 新增 ai_agent 表
     │
     ▼
Agent Instance     ← 状态机版新建 ai_agent_instance；DAG 版复用 ai_flow_run
     │
     ▼
Execution Context  ← 扩展现有 OrchestrationContext 为分区上下文
     │
     ▼
Agent Memory       ← 复用 ai_memory + AgentMemory，补 Import/Export 钩子
```

### 1、Agent Definition（智能体定义）— 新增

静态定义，**独立建表 `ai_agent`**（决策 2）。它不是 Flow 的别名，而是对 Flow 的一层封装：

一个 Agent 保存：

- `flow_code` + `flow_version`：引用哪个编排图（可换绑版本，做灰度）
- **输入契约** `input_schema`：Agent 对外暴露的入参（JSON Schema）
- **输出契约** `output_schema`：Agent 对外返回的结构
- **记忆配置** `memory_config`：是否启用长期记忆、Import/Export 策略（Replace/Append/Summary）
- Prompt / 默认模型档案等运行默认值
- 权限、启用状态

> 为什么不复用 Flow？因为 Flow 是**纯编排结构**（节点+边），可被多个 Agent 以不同的记忆策略、不同的 IO 契约复用。Definition 一旦发布**版本不可变**（改动 = 新版本），类似：
>
> ```java
> class TravelAgent {}
> ```

### 2、Agent Instance（智能体实例）

每次执行产生一个新 Instance。点击执行、API 调用、定时任务，本质都是创建新 Instance。

**修订点（对齐现状）**：v1 说 Instance 生命周期是"创建→执行→结束→**销毁**"。实际后端的 `AiFlowRun` 是**持久化、可 resume 的**。修订版明确：

```text
创建 → 运行 →（可挂起：等待事件 / Human-in-the-loop）→ 完成 / 失败
                    │
                    └── 全程落库，支持续跑与回放
```

Instance **不销毁**，落库保留用于续跑、审计、回放。销毁的只是内存中的运行时对象。

**版本锁定（决策）**：Agent 定义版本不可变，改配置 = 发新版本。**运行中的旧实例锁定其创建时的 `agent_version` / `flow_version`，跑完即弃，不迁移到新版本**。

**版本锁定如何真正生效（关键，决策 v3）**：仅在实例上落 `flow_version` 号 **不足以**锁定版本——因为后端的 `ai_flow_node` / `ai_flow_edge` 表只挂 `flow_code`、**不按版本存历史快照**（改流程 = 原地覆盖节点/边）。若续跑时回查这两张表，加载到的是**被改过的最新节点定义**，版本锁形同虚设。

因此状态机实例采用 **graph_snapshot 自包含**：创建实例时把**编译后的完整图定义**（节点 + 边 + 每个节点的 `stateConfig` + guard 表达式）快照进 `ai_agent_instance.graph_snapshot`。**续跑 / 回放只从 snapshot 加载图，绝不回查 node/edge 表**，天然免疫"别人改了流程"。此时 `flow_version` 降为**审计标记**（记录"从哪个版本创建"），运行时不依赖它查表。

> DAG 侧（`ai_flow_run`）续跑仍回查 node/edge 表，存在同样的版本漂移风险——这是**既有技术债**，不在本次范围；状态机侧用 `graph_snapshot` 规避。

**记忆隔离与版本（决策 v3）**：长期记忆按 **`agent_code`（不含 version）** 隔离，**同一 Agent 的所有版本共享同一份长期记忆**。理由：长期记忆是"这个 Agent 对用户/领域的认知积累"，换个 prompt 版本不该失忆。v2 改记忆策略只影响 Import/Export **怎么读写**，不影响记忆**归属谁**；key 命名空间跨版本保持稳定，避免踩键。

> 状态机内核下，Instance 记录的不是"已执行节点集"，而是"**当前状态 + 状态转移历史**"（见 第七章）。

### 3、Execution Context（执行上下文）

运行时真正的核心，所有节点（Tool / LLM / Agent / If / Loop）都只操作它。

**现状**：`OrchestrationContext` 已有 `attributes`（黑板）+ `nodeResults`（节点轨迹）+ `userId`/`conversationId`，并实现了 `ToolContext`。

**修订点**：扩展为**分区上下文**，把 v1 提出的分区落到具体字段上：

```text
ExecutionContext（扩展 OrchestrationContext）
│
├── Inputs        开始节点输入            → 现 attributes 中的入参，独立成区
├── Variables     流程变量               → 现 attributes 主体
├── Messages      LLM 对话消息           → 新增（现由 AgentMemory window 承载，需下沉到 context）
├── Artifacts     文件产物（pdf/image…） → 新增（**只存对象存储 key，不存内容**）
├── LocalMemory   本次执行的临时数据      → 新增（仅当前 Instance）
├── Metadata      TraceId/StartTime/TokenUsage/RetryCount → 部分已有，补齐
└── Outputs       Workflow 输出          → 新增（对齐 output_schema）
```

**兼容策略**：不推翻 `attributes`，而是在其之上提供分区视图 API（`inputs()`/`variables()`/`messages()`/`outputs()`…），底层仍是 map，避免破坏现有节点执行器。

**Artifacts 存 key（决策）**：`Artifacts` 分区里每个条目只存对象存储的 key/URL（如 `oss://bucket/xxx.pdf`）+ 元信息（文件名、mime、大小），**绝不把文件字节放进 context**。因此 `ai_agent_instance.context_snapshot` 体积可控，长循环下不会因 Artifacts 膨胀。

**snapshot 分级落盘（决策 v3，防写放大）**：自我审查这类循环可能转移几十上百次，若"每次转移都全量重写 `context_snapshot`"就是 O(n²) 写放大（`Variables`/`Messages` 在多轮 LLM 对话下持续增长）。策略：

- **RUNNING 中的普通转移**：只 **append 一行 `transition`**（轻量），`context_snapshot` **不刷新**。
- **全量刷新 `context_snapshot` 仅发生在**：① 挂起（SUSPENDED）② 越过检查点 ③ 终态（SUCCESS/FAILED）。刷新时同步记 `context_snapshot_seq =` 全量刷新时刻的**最大 transition seq**（含 RETRY 行；重放时再按 `outcome` 过滤，逻辑不冲突）。
- **崩溃恢复**：加载"最近全量 snapshot"，再增量重放 `seq > context_snapshot_seq` 的转移，回到断点（重放的正确性见下方「恢复语义」四铁律）。

> **`node_result` = 该步对 context 的完整变更集（delta），不是"随便一个返回值"**：一个节点可能往黑板写多个 key（现有模型下至少是 `outputKey` 那一个，未来可扩为多键 delta）。增量重放靠 apply 这个 delta 重建 context——**若只存 LLM 返回文本而丢掉别的写入，重放会漏产物**。实现节点执行器时，`node_result` 必须上报"这一步改了 context 的哪些 kv"，而非仅 LLM 原始输出。

这样长循环只追加轻量转移行，不重复重写大 TEXT，写入随转移次数线性增长。

**恢复语义（决策 v3，必须严格实现，否则重放会污染状态）**：分级落盘 + 重试轨迹 + graph_snapshot 三者叠加后，崩溃恢复的正确性靠以下四条铁律保证：

1. **恢复顺序**：① 从 `graph_snapshot` 载入图定义 → ② 注入 `inputs`（初始入参，`context_snapshot` 初始为空时的唯一数据源）→ ③ 载入 `context_snapshot`（可能为空，`context_snapshot_seq=-1` 表示还没全量快照）→ ④ 重放 `seq > context_snapshot_seq` 的增量 transition。
2. **只重放 `outcome=SUCCESS` 的行**：`outcome=RETRY/FAILED` 行的 `node_result` 存的是**错误摘要不是产物**，重放它们会把错误当产物写进 context。恢复时**必须过滤，只用 SUCCESS 行的 node_result 恢复产物**。
3. **重放 = 恢复产物，不是重新执行**：增量重放只把 SUCCESS 行的 `node_result` 写回 ExecutionContext，**绝不重新调 LLM / 工具**（它们不幂等，重放会重复副作用、重复计费）。
4. **先干活后记账**：一个节点的 context 写入 / 外部副作用**必须在** transition 落盘**之前**完成。保证"transition 里有 SUCCESS 记录 ⇒ 该步一定已干成"，反之崩溃在记账前则该步视为未发生、恢复后重跑。

> **状态机只保证 at-least-once，不保证 exactly-once**（现实约束，别指望补偿兜住一切）：铁律 4 存在一个无法消除的窗口——外部副作用（扣款）成功但 transition 落盘前崩溃。恢复后该步被判"未发生"重跑 → **重复副作用**；且补偿栈扫的是已落盘的 SUCCESS 转移，**这条没落盘的记录扫不到 → 漏补偿**。因此：**凡有外部副作用的节点，必须自带幂等键（idempotency key，如 `instanceId+nodeCode`）**，靠下游服务用幂等键去重来实现 exactly-once。状态机层不承诺 exactly-once，阶段 2.5 补偿也不能替代下游幂等。

### 4、Agent Memory（长期记忆）— 复用

每个 Agent 拥有一份按 `agentCode` 隔离的长期 Memory，互不影响。

**现状**：`AgentMemory` + `DatabaseLongTermMemory` + `ai_memory` 表已落地（见 memory 记录 `ai-longterm-memory-db`），博客 Agent 已启用。

生命周期：Agent 创建 → 一直存在 → Agent 删除 → Memory 删除。

## 三、执行流程（引入 Memory Import/Export 钩子）

**这是本设计相对现状真正新增、且有价值的部分。** 现有 `FlowEngine.run()` 没有"实例启动时导入长期记忆、结束时导出记忆变更"这两个钩子。

```text
【首次创建分支】                          【续跑/唤醒分支】
创建 Instance                            load ai_agent_instance
   ↓                                        ↓
Import Agent Memory（读 ai_memory）        从 graph_snapshot + context_snapshot
   ↓                                        + 增量重放 恢复 ExecutionContext
写入首个 context 基线并落一次              （★不重新 Import Memory）
context_snapshot（冻结 Import 结果）           ↓
   └──────────────┬───────────────────────────┘
                  ↓
        执行内核（Dag | StateMachine）
                  ↓
        Export Memory（按 memory_config 写回 ai_memory）
                  ↓
        完成 / 挂起 / 失败（落库）
```

**铁律**：执行过程中所有节点**只操作 ExecutionContext**，绝不直接写 Agent Memory。所有长期记忆变更统一在 Export 阶段落盘。

原因（v1 已述，保留）：一个 Agent 可能同时运行多个 Instance，若各自直接 `agentMemory.put(...)` 会产生覆盖 / 数据冲突 / 并发问题。统一 Export 规避此类问题。

**Import 冻结进实例（决策 v3，与 graph_snapshot 自包含对齐）**：Import 是**仅在首次创建时的一次性动作**，其读到的 Memory 值**立即写入首个 context 基线并冻结**（落一次 `context_snapshot`，`context_snapshot_seq=0` 之前）。**续跑/唤醒时绝不重新 Import**——因为长期记忆按 `agent_code` 跨实例共享、在本实例挂起期间可能被别的实例改动（记忆漂移），重新 Import 会拿到不同的值，破坏"实例锁定创建时状态"的自包含承诺。即：**记忆的"读"在创建时定格，记忆的"写"在 Export 时发生**，中间的续跑不碰 ai_memory。

## 四、Memory 生命周期

### Import（导入）
实例启动时，按 `memory_config.import` 从 `ai_memory` 读取（如 `userProfile`），写入 `ExecutionContext.Variables`。

> **与 Inputs 的 key 冲突（决策 v3）**：Import 先写、Inputs 后写，**同名 key 以 Inputs 为准**（本次调用的显式入参优先于历史记忆）。

### Runtime（运行）
节点始终操作 `context.put("travelPlan", result)`，**不碰** `agentMemory.put(...)`。

### Export（导出）
实例结束时生成 Memory Changes，按策略写回：

- **Replace**：覆盖同 key
- **Append**：追加
- **Summary**：先 LLM 摘要再写入（对应 v1 "Memory Strategy"）

```json
{ "summary": "用户喜欢东京", "preference": { "city": "东京" } }
```

> **Export 失败不翻盘实例终态（决策 v3）**：实例业务已跑完（终态 SUCCESS），Export 写 `ai_memory` 时 DB 抖动失败——**实例终态仍记 SUCCESS**，Export 失败记 warning + 落重试队列（或下次同 Agent 实例启动时补偿性重导）。理由：业务产物（Outputs）已落 `ai_agent_instance`，不能因"记忆没存上"就把已成功的业务判失败。记忆是尽力而为的旁路，不是业务成败的判据。：重试 / 超时 / 错误转移 / 补偿（决策 4）

状态机的每个 State（节点）除"做什么"外，还可配置"失败了怎么办"。**全部落在现有 `ai_flow_node.node_config` 的 `stateConfig` 段**，不新增表列（决策：全进 node_config JSON）。

### 4·5.1 三类能力的本质区分（先厘清，避免混淆）

| 能力 | 本质 | 作用范围 | 落地层 |
|---|---|---|---|
| **重试 Retry** | 同状态失败后**原地再试** N 次 | 状态内部，不改图结构 | `node_config` |
| **超时 Timeout** | 执行超时则判失败 | 状态内部 | `node_config` |
| **错误转移 onError** | 失败作为**一种事件**触发特定转移 | 复用转移机制 | `node_config` → 指向 errorState |
| **补偿 Compensation** | 失败/回滚时执行**反向操作**（Saga） | 跨状态，维护补偿栈，有副作用才有意义 | 预留，见 4·5.4 |

> **关键认知**：重试/超时/错误转移是"状态自己的属性"，塞进 node_config，**不污染内核图结构**。补偿是 Saga 模式，需要内核维护"已成功副作用状态栈"并反向执行，复杂度高一个数量级，且**只在有外部副作用时才有意义**。

### 4·5.2 stateConfig 结构（重试/超时/错误转移，阶段 1 实现）

```jsonc
// ai_flow_node.node_config 内的 stateConfig 段
{
  "stateConfig": {
    "retry":   { "maxAttempts": 3, "backoffMs": 1000, "on": ["TIMEOUT", "TOOL_ERROR"] },
    "timeoutMs": 30000,
    "onError": "GOTO_STATE",       // FAIL_INSTANCE（默认）| GOTO_STATE | SUSPEND
    "errorState": "human_review"   // onError=GOTO_STATE 时目标状态
  }
}
```

### 4·5.3 内核执行单个状态的伪逻辑

```text
执行状态 S:
  attempt = 0
  loop:
    try（带 timeoutMs 熔断）:
      result = 执行节点（PROMPT / TOOL / AGENT …）   // 干活：调 LLM/工具
      apply result 的 delta → ExecutionContext        // ① 先写 context（铁律4：先干活）
      落 transition{to=S, attempt, outcome=SUCCESS,     // ② 后记账（context 写完才落账）
                    node_result=context delta}
      → 选下一转移：按 condition_expr(guard) 匹配 S 的出边（裁决规则见 5.3 下方）
    catch 失败:
      落 transition{to=S, attempt, outcome=RETRY|FAILED, node_result=错误摘要}  // 失败也记一行
      attempt++
      if attempt < retry.maxAttempts 且错误类型 in retry.on:
        退避 backoffMs 后重试
      else 按 onError:
        FAIL_INSTANCE → 实例置 FAILED，落库结束
        GOTO_STATE    → 转到 errorState（复用转移机制，失败即事件）
        SUSPEND       → 挂起等 signal（人工介入，阶段 3 能力）
```

> 顺序铁律（对齐 二·3「恢复语义」铁律 4）：**先 apply context delta，再落 transition**。保证"库里有 SUCCESS 行 ⇒ context 一定已写"，崩溃在记账前则该步视为未发生、恢复后重跑。

> **重试落审计轨迹**：每次 attempt（含失败）落一行 `transition`，`from_state = to_state`（原地），`outcome=RETRY`，`node_result` 记该次错误摘要——排障可见"重试几次、每次为何失败"，回放时按 `outcome` 折叠。`onError=GOTO_STATE` 复用第五章的转移机制，把"失败"当成一种事件转到任意状态（人工审核 / 降级分支）。

### 4·5.4 补偿（Saga）— 架构预留，实现延后到"有副作用的 Agent"

**为什么不在阶段 1 做**：补偿只在流程有**外部副作用**（扣款、发消息、建单）时才有意义——失败要执行反向操作回滚。阶段 1 的 demo 是**内容生成自我审查循环**（纯计算、幂等、无副作用），**没有可补偿的东西**。强行在纯计算流程里做补偿只能造假场景，属返工。

**预留设计**（不实现，仅定义扩展点，架构不推翻）：

```jsonc
// node_config.stateConfig 预留段
{ "compensation": { "action": "TOOL", "toolCode": "refund", "inputMapping": { "orderId": "orderId" } } }
```

- `ai_agent_instance_transition` 预留 `is_compensation TINYINT` 列（第七章 DDL 已可加），标记补偿轨迹。
- **"补偿栈"是从 transition 历史派生的视图，不是内存态**（关键）：实例可能挂起数天或崩溃恢复，内存栈会丢失。回滚时**实时扫库重建**——取 `last_checkpoint_state` 之后、`is_compensation=0`、`outcome=SUCCESS` 且对应节点配了 `compensation` 的转移，按 `seq` **逆序**逐个执行反向动作。这样补偿能力对挂起/恢复天然免疫，无需持久化额外的栈结构。

**排期**：补偿实现绑定到**阶段 2.5**——待出现首个带副作用的 Agent（如"下单 Agent"）时落地，届时 demo 换成"下单失败→补偿退款"才有说服力。见第十二章。

### 4·5.5 检查点与回滚粒度（决策：回滚到检查点，非全量）

补偿**不是**"实例失败就把所有做过的副作用全部反向回滚"，而是**回滚到最近的检查点（Checkpoint）**。这更贴合真实业务——有些副作用是"已确认、不该回滚"的，检查点就是它们的分界线。

- **Checkpoint（检查点）**：状态机中的一种标记，表示"此前的副作用已确认稳定，回滚不越过此点"。落在 `node_config.stateConfig.checkpoint = true`，或作为一类特殊 State。越过检查点时把状态机当前状态写入 `ai_agent_instance.last_checkpoint_state`。
- **回滚作用域 = 查询下界，不是"清空内存栈"**（对齐 4·5.4 的派生视图）：补偿栈是从 transition 历史**扫库派生**的，没有内存态可清。"越过检查点即前面副作用不再参与回滚"这一语义，**靠 `last_checkpoint_state` 作为扫库的下界天然实现**——回滚时只扫 `last_checkpoint_state` 之后的 SUCCESS 转移，之前的自然被排除，无需任何"清空"动作。

```text
[下单]✔压栈  ──▶  [支付]✔压栈  ──▶  ★检查点(清栈)  ──▶  [发货]✔压栈  ──▶  [通知]✘失败
                                                                              │
        失败只回滚检查点之后：补偿[发货]（退货），不碰[下单]/[支付]（已过检查点，视为确认）
```

- 表支撑：`ai_agent_instance.last_checkpoint_state` 记录最近越过的检查点；`ai_agent_instance_transition.is_compensation` 标记补偿轨迹（两列 DDL 已含，阶段 2.5 启用）。
- 若整条链无检查点，则退化为"全量回滚"——即检查点是可选增强，不配置时行为符合直觉。

## 五、执行内核：DAG vs 状态机（决策 1 & 3 的核心）

### 5.1 为什么需要状态机

你要的是"流程的**状态机**"。DAG（现有 `DagOrchestrator`）**做不到**下面这些，因为它靠"入度归零 + executed 去重"推进，一旦成环入度永不为零、回跳的节点会被去重跳过：

- **回跳**：审批不通过 → 退回上一节点重做
- **成环**：反思 / 重试循环，直到满足条件才出环
- **等待外部事件**：Human-in-the-loop，挂起等人工输入后再推进

### 5.2 两个内核并存（决策 3）

在现有 `Orchestrator` 接口下新增状态机实现，与 `DagOrchestrator` 并列：

```text
Orchestrator（接口，已存在）
├── DagOrchestrator          有向无环，支持并行分支、逐节点续跑（已落地，保留）
└── StateMachineOrchestrator 单点状态推进，支持回跳/成环/挂起（新增）
```

Flow 定义上新增 **`engine_type`** 字段（`DAG` | `STATE_MACHINE`），`FlowGraphFactory` / `FlowEngine` 据此选择内核。**对 Agent 层透明**。

### 5.3 状态机语义定义

| 概念 | 含义 |
|---|---|
| **State（状态）** | 一个节点即一个状态；有唯一 `entry`（入口态）与若干 `terminal`（终态） |
| **Transition（转移）** | 有向边，携带 **guard**（SpEL 条件，复用现有 `ConditionCompiler`）与可选 **event**（触发事件名） |
| **当前状态指针** | Instance 始终"处于某一个状态"，而非 DAG 的"一批就绪节点" |
| **回跳** | Transition 的 `to` 指向拓扑上更早的 State，合法 |
| **成环** | 允许 State 经若干 Transition 回到自身或前驱，靠 guard 决定是否出环 |
| **挂起（SUSPENDED）** | 状态需要外部事件才能转移时，Instance 落库挂起。可同时**等待多个事件之一**（如 approve/reject/request-changes），落 `awaiting_events`(JSON数组)；`signal(instanceId, event, payload)` 的 `event` 命中其一即唤醒，由 guard + payload 决定去向 |
| **max_transitions** | 全局转移次数上限（`ai_flow.max_transitions`，per-Flow 可配，默认 100），防死循环。**超限 → 实例置 FAILED**（决策：不转兜底状态，行为简单可预期），`error_msg` 记 "exceeded max_transitions" |

**实例级并发控制（决策 v3，必须实现）**：`signal` / `resume` 都是可能**并发进入**的入口（外部异步回调、两个审批人同时点、崩溃后多节点抢续跑），必须用**状态 CAS 抢占**，靠 `lock_version` 乐观锁兜底：

```sql
-- 唤醒挂起实例：只有 SUSPENDED 才能被抢占为 RUNNING，影响行数=0 则拒绝（已被别的 signal 抢先）
UPDATE ai_agent_instance SET status='RUNNING', lock_version=lock_version+1
WHERE instance_id=? AND status='SUSPENDED' AND lock_version=?;
```

- **抢占成功（影响 1 行）**：本次 signal/resume 获得推进权，独占执行状态机。
- **抢占失败（影响 0 行）**：说明状态已变（别的 signal 抢先、或已不是可唤醒态），**直接拒绝，不推进**——绝不并发跑同一实例。
- `resume` 同理：CAS `WHERE status='RUNNING'(判活/超时)`，防两个进程同时续跑一个崩溃实例。

**编图校验（阶段 1 硬前置，`FlowGraphFactory` 编 STATE_MACHINE 图时执行）**：状态机起步和终止靠 `state_type`，编图时必须校验，不合法直接拒绝建图（Fail-Fast，别等运行时才炸）：

- **ENTRY 恰好一个**：`state_type=ENTRY` 的节点有且仅有 1 个——0 个则不知从哪起步，>1 个则起点歧义。
- **TERMINAL 至少一个**：至少 1 个 `state_type=TERMINAL`，否则状态机永不正常收尾（只能靠 max_transitions 兜底 FAILED，非预期）。
- **可达性**（建议）：每个非 ENTRY 节点应从 ENTRY 可达，孤立节点告警。

**转移裁决（阶段 1 内核核心分支，必须定义清楚）**：一个状态成功后，在其**出边**中选下一个转移的规则：

- **按 `sort_no` 升序逐条求值 guard，取第一个为 true 的边**（复用现有 `ai_flow_edge.sort_no` 排序 + `condition_expr` 求值，与 DAG 分支一致）。
- **空 `condition_expr` = 无条件恒真**，通常作为排在最后的 default 边（else 分支）。
- **零匹配**（所有出边 guard 全 false 且无 default）：**当前状态非 TERMINAL 却走投无路 → 实例置 FAILED**，`error_msg` 记 "no matching transition at state X"。不静默停在原地（那会与挂起混淆）。
- **多匹配**：不报错，**首个命中即转移**（短路），后续边不再求值——所以 default 边必须放最后。
- **TERMINAL 状态无出边**：到达即实例 SUCCESS，不再选边。

### 5.4 与 DAG 的能力取舍（必须知情）

选状态机内核 = 用以下 DAG 能力换回跳/挂起能力：

- **失去并行分支**：状态机是单点推进，天然串行（如需并行，用 DAG 内核或未来引入并行子状态）。
- **续跑语义不同**：DAG 续跑 = "跳过 executed 节点"；状态机续跑 = "恢复到 current_state"，具体走"snapshot + 增量重放 SUCCESS 转移"四步（见 二·3「恢复语义」）。因此状态机**另建实例表**（第七章），不复用 `ai_flow_run` 的 `executed_nodes` 语义。
- **loop 容器节点**：前端已有的 loop 节点，在状态机内核下等价于"guard 成环"，更自然。

## 六、Workflow Agent（静态递归）与动态多智能体

v1 核心卖点：Agent 节点可引用另一个 Flow，形成递归组合。当前 `AgentNodeExecutor` 已支持同步执行子 Agent、Input/Output Mapping、递归深度限制和循环引用检测。这是**编排时已经确定子 Agent 的静态调用**。

`AgentNodeExecutor` 契约：

- 节点配置 `refAgentCode`（或 `refFlowCode+version`）
- **Input Mapping**：父 context 的字段 → 子 Agent 的 `input_schema`（决策：默认**不共享 Memory**，只传映射入参）
- 子 Agent 独立创建 Instance、独立 Import/Export 自己的 Memory
- 子 Agent 的 Outputs 按 **Output Mapping** 写回父 context

```text
Agent A (city, budget) ──Input Mapping──▶ Agent B(输入 city,budget)
                                              │
Agent A ◀──Output Mapping── travelPlan ◀──── 输出 travelPlan
```

递归深度上限（`ai_flow.max_agent_depth`，默认 8）、循环引用检测（A→B→A）作为治理项。

**当前实现边界（v4 核实）**：同步子 Agent 可以跑到终态；若子 Agent `SUSPENDED`，当前执行器仍会报错，异步父子编织尚未闭环。不能把“父子关联字段已落库”表述成“异步父子生命周期已完成”。

递归 + 挂起 + 持久化三者叠加时，父子实例的编织不能靠内存阻塞调用，否则父进程崩溃后子实例跑完无人接、恢复重跑 AgentNode 会重建子实例、老子实例成孤儿。完整策略：

- **父子关联落库**：子实例落 `parent_instance_id` + `parent_node_code`（DDL 已含），形成可追溯的实例树。
- **子挂起 → 父挂起**：子 Agent SUSPENDED 时，父实例在该 AgentNode 上**也转 SUSPENDED**，`awaiting_events` 等待"子实例完成"事件。
- **子完成 → 持久化事件唤醒父**：子实例进终态时，先固化结果，再通过内部 Task 终态事件按 CAS `signal` 父实例；这不是对外 Webhook。
- **恢复幂等**：动态委派按 `(parent_instance_id, parent_state, dispatch_key)` 查 `ai_agent_task`；静态 AgentNode 至少按父实例+父节点查存量子实例。有则挂接不重建，无则新建。

对话中由 Lead Agent 临时决定“启动几个程序 Agent、分别做什么、是否并行”属于**动态多智能体协作**，不继续扩张 `AgentNodeExecutor`。它通过 `spawn_agent` / `wait_agents` / `collect_results` 等受治理工具创建可靠 Agent Task，完整设计见：

> **[多智能体协作层设计.md](./多智能体协作层设计.md)**：Lead-Worker 模型、`ai_agent_task`、父子挂起恢复、工作区隔离、并行任务 DAG 和程序开发协作。

## 七、数据模型（DDL 方案）

> 命名沿用 `ai_` 前缀、`ai-flow` store 模块的风格（`@TableName`、`FieldFill`、JSON 列以字符串存 + `FlowJsonCodec`）。
>
> **决策 3（1:N 复用 + 表可重构）落地**：`ai_agent` 通过 `flow_code + flow_version` 引用编排图，多个 Agent 可引用**同一个 Flow**（1 Flow : N Agent），各自带不同的记忆策略 / IO 契约 / 模型档案。Flow 表不反向持有 Agent，保持"Flow 是纯编排结构、可被复用"。既然允许重构，Agent 与 Flow 之间**不建中间关联表**，靠 `ai_agent.flow_code` 外键式引用即可表达 N:1。

### 7.3 新增 `ai_agent_instance`（状态机实例）

```sql
  UNIQUE KEY uk_instance_id (instance_id),
  KEY idx_parent (parent_instance_id)
) COMMENT='AI 智能体执行实例（状态机）';

CREATE TABLE ai_agent_instance_transition (
  id             BIGINT       PRIMARY KEY AUTO_INCREMENT,
  instance_id    VARCHAR(64)  NOT NULL,
  seq            INT          NOT NULL COMMENT '转移序号，从 0 递增（重试也占序号）',
  from_state     VARCHAR(64),
  to_state       VARCHAR(64)  NOT NULL,
  event_name     VARCHAR(64)           COMMENT '触发本次转移的事件（如有）',
  attempt        INT          NOT NULL DEFAULT 0 COMMENT '进入 to_state 的重试次数（0=首次）',
  outcome        VARCHAR(16)  NOT NULL DEFAULT 'SUCCESS' COMMENT '轨迹类型：SUCCESS | RETRY | FAILED | COMPENSATED，回放时可折叠 RETRY 行',
  is_compensation TINYINT     NOT NULL DEFAULT 0 COMMENT '预留：1=补偿轨迹（Saga 回滚，阶段 2.5 启用）',
  node_result    TEXT                  COMMENT '进入 to_state 后该节点产物；失败/重试时记错误摘要（恢复时只重放 outcome=SUCCESS 行）',
  create_time    DATETIME,
  UNIQUE KEY uk_instance_seq (instance_id, seq)
) COMMENT='AI 智能体状态转移历史（回放/审计），每次 attempt 落一行';
```

> **版本锁定**：`graph_snapshot` 是自包含运行的核心——续跑/回放只从它加载图定义，与最新流程互不干扰，`flow_version`/`agent_version` 仅作审计标记。
> **审计完整**：每次 attempt（含重试失败）都落一行 transition，`outcome=RETRY` 标记中间失败，排障时可见"重试了几次、每次为啥失败"；回放时可按 `outcome` 折叠。
> **补偿预留**：`is_compensation` 阶段 1 恒为 0，阶段 2.5 Saga 落地时启用；`last_checkpoint_state` 同期启用。
> **取消预留（v4）**：阶段 5 增加协作任务后启用 `CANCEL_REQUESTED/CANCELLED`。取消是到安全检查点协作停止，不以强杀 Java 线程作为正常语义；取消状态变化同样产生内部生命周期 Outbox 事件。

> `ai_flow_run` / `ai_flow_run_node`（DAG 版实例）**保留不动**，供 `engine_type=DAG` 的 Flow 继续用。两套实例表按内核分流。

## 十一、整体架构

```text
                        Project
                           │
              ┌────────────┼────────────┐
          Travel Agent  Coding Agent  Customer Agent   ← ai_agent（定义）
              │  └Memory    └Memory       └Memory       ← ai_memory（按 agent_code 隔离）
              ▼
       Create Instance                                  ← ai_agent_instance（状态机）/ ai_flow_run（DAG）
              ▼
     Import Agent Memory ──────────────┐
              ▼                        │
     ExecutionContext（分区黑板）        │  Runtime 只写 Context
      ┌────────┬────────┬────────┐     │  绝不直写 Memory
     LLM      Tool     Agent    If/Loop│
      └────────┴────────┴────────┘     │
              ▼                        │
     Export Memory ───────────────────┘
              ▼
     完成 / 挂起(等 signal) / 失败    ← 全程落库，可续跑/回放
```

动态多智能体建立在上述单实例语义之上，不绕过 Runtime：

```text
Conversation
   ▼
Lead Agent Instance
   ├── ai_agent_task → Coding Worker Instance  → 独立 Worktree
   ├── ai_agent_task → Test Worker Instance    → 集成工作区
   └── ai_agent_task → Review Worker Instance  → Read-only
          │
          └── 终态写 Task Result + 内部 Outbox → CAS 唤醒 Lead
```

因此单 Agent 的状态机恢复仍是底座；协作层只新增可靠委派、等待、并行和工作区，不发明第三套执行内核。
